# ریشه‌یابی خطاها و پیشگیری — ۲۷ اکتبر ۲۰۲۶

## وضعیت و دامنه

**در Git ثبت شد؛ نصب و پذیرش تولید انجام نشده است.** مالک بررسی `/admin/errors`، لحاظ اصلاحات چت‌های دیگر، رفع ریشه‌ای، ثبت دانش و commit روی `develop` را خواست.

مبنای شروع `3613a1303e4177f4b53a13e273abee4e2b739b7f` بود. تغییرات هم‌زمان فروش VPS.TC و گزارش Hermes تا `3eba2d2e` با fast-forward حفظ شدند؛ تاریخچه بازنویسی نشد. SHA نهایی از commit حاوی همین سند خوانده شود.

پنجرهٔ اولیهٔ پنل ۱۵۰ رکورد مختلط داشت: ۹۵ exception، ۵۵ incident و در بخش جدا ۱۵۰ رکورد 404. این اعداد حجم کل تاریخچه یا تعداد خطاهای تجربه‌شده توسط مشتری نیستند. فرمان‌های CLI قبلاً با GET ریشه و status=500 ثبت می‌شدند؛ بخشی از رکوردها به ابزار بررسی یا QA مربوط بود. زمان رکوردها UTC است. رکوردهای تاریخی پاک نشدند؛ متن خام لاگ، شناسهٔ مشتری/ماشین، دادهٔ مالی، IP و اعتبارنامه در این سند نیست.

## اصلاحات این تغییر

### همگام‌سازی طولانی در درخواست وب

fatal سقف اجرای ۳۰ ثانیه در POST مدیریتی همگام‌سازی دیده شد. `CloudController::sync` مستقیماً کاتالوگ‌ها یا قیمت‌ها را از API تأمین‌کنندگان می‌خواند؛ زمان شبکه و صفحه‌بندی در بودجهٔ درخواست وب جا نمی‌گیرد.

اکنون POST فقط یک درخواست پایدار ثبت می‌کند و برمی‌گردد. `cloud:refresh-requested` روی زمان‌بند موجود، دقیقه‌ای و در پس‌زمینه اجرا می‌شود. cron میزبان تازه‌ای لازم نیست؛ هیچ cron تولید در این کار تغییر نکرده است. مجوز admin و CSRF قبلی حفظ‌اند؛ staff یا مهمان نمی‌تواند کار ثبت کند.

- فرم تکراری در queued/running همان شناسه و نوع کار را برمی‌گرداند؛ درخواست قیمت، کار کامل در حال اجرا را عوض نمی‌کند.
- رسید خصوصی در `storage/app/cloud-catalog-refresh/state.json` با قفل کنترل و rename اتمی ذخیره می‌شود؛ کلید یا پاسخ خام تأمین‌کننده ندارد.
- قفل worker دو مصرف‌کننده را متوقف می‌کند. قفل مستقل catalog در خود `CloudCatalogSync::sync/reprice` مسیرهای زمان‌بند، FX و درخواست مدیر را سری می‌کند. قفل OS با خروج پروسه آزاد می‌شود؛ TTL مجوز هم‌پوشانی کار زنده نیست.
- برخورد با اجرای دیگر، درخواست را با زمان اولیه در صف نگه می‌دارد. کار بیش از ۱۵ دقیقه مانده در صف اجرا نمی‌شود و expired می‌شود.
- پس از قطع worker، اجرای بعد رسید running را interrupted/failed می‌کند. نتیجهٔ ناقص خودکار بازپخش نمی‌شود؛ درخواست تازه پس از بررسی رسید لازم است.
- شکست provider، نبود نرخ معتبر و هشدار هزینه با completed یکی نیستند. partial/failed، provider ناموفق، شمار پلن و هشدار هزینه/مقایسه در پنل می‌مانند. استثنا تنها با کلاس و شناسهٔ رسید گزارش می‌شود.
- رسید ناموفق در دقیقه‌های بعد شکست مصنوعی تازه نمی‌سازد؛ بدون بازپخش idle برمی‌گردد.
- سلامت، رسید ناموفق/ناخوانا، صف بیش از ۱۵ دقیقه و اجرای بیش از یک ساعت را با لینک پنل هشدار می‌دهد؛ heartbeat پایان کار را ثابت نمی‌کند.

فرمول قیمت، سیاست فروش، فاکتور، کیف پول، خرید و حذف ماشین بازطراحی نشده‌اند. همگام‌سازی کامل همچنان کاتالوگ محصولات را تازه می‌کند؛ پذیرش انتشار باید ابتدا رسید، رندر و اجرای خالی طبیعی worker را بررسی کند، نه اجرای دستی همهٔ فرمان‌ها.

### رقابت نوشتن و برش فایل خطا

کد قبلی فایل را بدون قفل می‌خواند و فقط هنگام جایگزینی قفل می‌گرفت. append موفق یک worker می‌توانست بین read و replace در دیگری قرار بگیرد و پاک شود. اکنون append/read/trim/write روی همان handle و زیر یک `LOCK_EX` انجام می‌شوند. خواندن قفل مشترک و clear قفل انحصاری دارد؛ بازکردن فایل برای clear پیش از گرفتن قفل آن را truncate نمی‌کند.

`JSON_INVALID_UTF8_SUBSTITUTE` مانع حذف بی‌صدای کل رکورد به‌خاطر بایت خراب پیام provider می‌شود. آزمون چندپروسه‌ای چهار نویسنده و ۶۴۰ رخداد، پنجرهٔ کامل و JSONهای معتبر را می‌سنجد.

### منشأ CLI و حفظ خطای وب

exception در CLI اکنون `source=console`، status/method/url خالی و هویت console دارد. فقط نام command مجاز ثبت می‌شود؛ آرگومان‌ها ممکن است کلید داشته باشند و ثبت نمی‌شوند. درخواست وب `source=http` دارد؛ متن شبیه پیام زمان‌بند آن را CLI نمی‌کند.

برای رکورد قدیمی فقط شواهد مشخص wrapper زمان‌بند، قاب `artisan` و فایل `Command line code`/`Standard input code` استفاده می‌شود. guest یا loopback منشأ را ثابت نمی‌کند؛ موارد نامعلوم در بخش وب می‌مانند و متن پنل محدودیت را توضیح می‌دهد.

حد نگهداری خطاهای وب، خرابی‌های گرفته‌شده و exceptionهای console مستقل و هرکدام ۴۰۰ است؛ ترتیب ورود در همان فایل حفظ می‌شود. 404 فایل جدا دارد. پنل در هر گروه حداکثر ۱۵۰ رکورد را پس از تفکیک نمایش می‌دهد. تکرار خرابی cron دیگر تنها خطای وب مشتری را از فایل یا پنل بیرون نمی‌اندازد. گروه‌ها در سلامت همچنان منظور می‌شوند؛ طبقه‌بندی CLI علت شکست command را رفع نمی‌کند.

## آزمون و جلوگیری از تکرار

اجرای اولیهٔ گسترده به‌علت تلاش برای اتصال خارجی پیامک توسط بررسی خودکار متوقف شد و نتیجهٔ کامل نیست. ادامه با `scripts/run-php-tests-offline.py` بود: seccomp در Linux ایجاد socket/ارسال شبکه را برای runner و فرزندان منع می‌کند و پیش از شروع، بسته‌بودن IPv4/IPv6 را می‌سنجد؛ در نبود isolation تست اجرا نمی‌شود. این ابزار فقط برای checkout توسعه است. `Http::fake` به‌تنهایی تمام SDKهای native را پوشش نمی‌دهد.

نمونه از `website/` با PHP و ini توسعه:

```bash
python ../scripts/run-php-tests-offline.py --php /path/to/php --ini /path/to/php.ini tests/Feature/CatalogRefreshRequestsTest.php tests/Feature/ErrorTrackerTest.php
```

baseline جدا و بدون تغییر: ۱۲۴ آزمون، ۱۰۷ موفق، ۸ failure، یک error و ۸ skip. همان نام‌های شکست روی نسخهٔ تغییرکرده، پیش از اصلاح fixtureها بازتولید شدند. دو مجموعهٔ قدیمی CloudCatalog/CloudAdminControls هنوز به override دستی و نبود snapshot متکی بودند؛ اکنون نرخ ذخیره‌شدهٔ نوسان و snapshot متناظر می‌سازند. انتظار قدیمی عنوان تنظیمات با وجود گروه اتصال واقعی در آکاردئون جایگزین شد؛ assertionهای قیمت، ارزان‌ترین عرضه و مسدودسازی provider حذف نشدند. guard تولید برای سبزشدن تست ضعیف نشد.

نهایی با PHP 8.4.27 و SQLite ایزوله: **۱۴۵ آزمون، ۱۳۷ موفق، ۵۴۱ assertion، صفر failure/error و ۸ skip**. skipها به decoder مورد اعتماد ورودی ویدئو در AiMediaRelay مربوط‌اند. اجرای MariaDB، مرورگر رابط تازه و پذیرش واقعی provider/تولید انجام نشد. [خلاصهٔ ماشینی](error-reliability-2026-10-27/validation.json) مجموعه‌ها و نتیجهٔ واقعی را دارد؛ خروجی خام آزمون/تولید وارد Git نشده است.

## انتشار قابل بررسی و بازگشت

[manifest](error-reliability-2026-10-27/manifest.json) فقط ۱۳ فایل runtime را مشخص می‌کند؛ تست، مستند، runner، `.env`، vendor، داده و log در بسته نیستند. hash مبنا از Git است و هم‌هشی تولید را ثابت نمی‌کند. اختلاف تولید باید پیش از نصب تطبیق داده شود؛ به‌ویژه `bootstrap/app.php`، `routes/console.php` و Hermes فعال نباید با نسخهٔ کامل مخزن بازنویسی شوند.

ادامهٔ مجاز: خواندن فقط فایل/بخش لاگ مرتبط و hash نسخهٔ فعال، تطبیق اختلاف، پشتیبان خصوصی، قفل انتشار، نصب محدود و فعال‌سازی هدفمند، سپس رندر و رسید اجرای خالی طبیعی. اجرای دستی `schedule:run`، گردش مالی، خرید/حذف ماشین، migration، پیامک یا cache flush عمومی پذیرش این بسته نیست.

در این نشست API خواندن فایل تولید به‌علت نبود مجوز صریح این دسترسی مدیریتی در بررسی خودکار رد شد. پس از آن مسیر جایگزین برای همان دسترسی امتحان نشد؛ انتشار متوقف ماند. اصلاحات بالا «نصب شد» یا «در تولید تأیید شد» گزارش نمی‌شوند.

بازگشت فایل از پشتیبان همان انتشار و با guard هش است. پیش از برگرداندن worker/route، رسید queued/running بررسی شود تا کار بی‌صاحب نماند. رسید، قفل runtime و log برای rollback کور پاک نشوند. این بسته migration ندارد؛ rollback فایل، اثر احتمالی همگام‌سازی محصولات را برنمی‌گرداند و داده/قیمت باید جدا تطبیق داده شود.
