# استاندارد همکاری تیم ServerNet

این سند استاندارد پیشنهادی/مستندشدهٔ همکاری است؛ وجودش به معنی فعال‌شدن تنظیمات GitHub یا انتصاب افراد نیست. شاخهٔ مرجع مورد تأیید مالک **develop** است.

## ۱. مدل کار و مسئولیت

اکنون مالک اعلام کرده تمام توسعه‌دهندگان روی develop کار می‌کنند. برای کاهش برخورد، مسیر توصیه‌شده برای تغییرهای بعدی، شاخهٔ کوتاه‌عمر از develop و PR با **base=develop** است؛ main وارد جریان انتشار نمی‌شود. تا زمان پذیرش این مدل، commit مستقیم باید کوچک، هماهنگ و بدون بازنویسی تاریخچه باشد.

```bash
git fetch origin
git switch develop
git pull --ff-only origin develop
# فقط روی worktree تمیز و برای کار جدید
git switch -c docs/topic-name
```

پیش از merge، جدیدترین develop و diff کامل بررسی شود. برنچ قدیمی یا default branch به‌صورت ضمنی مبنای diff نباشد. عملیات destructive مثل force-push، reset --hard روی کار مشترک و پاک‌کردن تغییر دیگران روش حل تعارض نیست.

| مسئولیت | وظیفه | وضعیت تعیین شخص |
|---|---|---|
| مالک محصول | تصمیم مالی، سیاست سرویس، مجوز تغییر حساس و پذیرش ریسک | مالک پروژه؛ جانشین باید ثبت شود |
| توسعه‌دهنده | تغییر محدود، تست، مستند و طرح بازگشت | برای هر کار مشخص شود |
| بازبین | بررسی مستقل کد، داده، امنیت و شواهد تست | برای هر PR مشخص شود |
| مسئول انتشار | یک نفر در پنجرهٔ انتشار، کنترل manifest و ثبت نتیجه | باید قبل از انتشار مشخص شود |
| مسئول زیرساخت/داده | تغییر host، backup، migration و عملیات مستقل | فهرست افراد و دسترسی‌ها هنوز تکمیل نشده |

این نقش‌ها می‌توانند در تیم کوچک بر عهدهٔ یک نفر باشند، اما برای تغییر پول/داده/مجوز، بازبینی مستقل توصیه می‌شود. نام یا دسترسی فردی از روی حدس اضافه نشود.

## ۲. یک کار، یک محدوده

در شرح کار بنویسید: مسئله، نتیجهٔ مورد انتظار، مسیرهای مجاز، مسیرهای ممنوع، ریسک، آزمون و نیاز انتشار. تمیزکردن پوشه، اصلاح UI و تغییر مالی را در یک تغییر مخلوط نکنید.

فایل‌های پرتعارض مانند `routes/web.php`، `routes/console.php`، `app/helpers.php`، layoutها و فایل‌های `lang/*/ui.php` پیش از کار با همکار هماهنگ شوند. مستند در `docs/project/` قرار گیرد، نه یک گزارش بی‌نام یا کپی پراکنده در public.

برای کدهای n8n، Worker و Ansible نیز diff، review و نسخهٔ مبنا لازم است؛ تغییر فقط در داشبورد، دانش تیم را ناقص می‌کند. انتقال کد بازبینی‌شده به داشبورد انتشار جداست، نه حذف مرحلهٔ Git.

## ۳. طبقه‌بندی ریسک

| سطح | نمونه | شرط پذیرش |
|---|---|---|
| کم | اصلاح متن راهنما یا لینک مستند | صحت محتوا/لینک و عدم تغییر رفتار |
| معمول | نمایش و UI بدون اثر مالی/دسترسی | سه زبان، تست رفتار مرتبط، بررسی JavaScript و cache |
| حساس | صورتحساب، کیف پول، شروع/حذف سرویس، احراز، webhook، migration، شبکه | بازبینی مستقل، تست مرزی/idempotency، طرح خطا و rollback؛ مجوز صریح عملیات تولید |

«کم‌ریسک» دربارهٔ مستند به معنی اجازهٔ درج راز یا دادهٔ مشتری نیست. مخزن هنگام بررسی عمومی بود؛ خروجی تشخیصی قبل از commit باید پاک‌سازی اطلاعات حساس شود.

## ۴. قراردادهای لازم برای تغییر کد

- سه زبان در همان تغییر تکمیل شوند؛ کلید خام ترجمه و لینک بی‌زبان پذیرفته نیست.
- واحد پول در ورودی، ذخیره و خروجی روشن باشد. حساب پولی با float یا تبدیل ضمنیِ واحد بازطراحی نشود؛ طرح دادهٔ موجود ملاک است.
- تحویل/تمدید/لغو، idempotency و reconciliation داشته باشند. پاسخ خالی/مبهم provider به موفقیت تبدیل نشود.
- تغییر provider علاوه بر مسیر خوش‌بینانه، timeout، ظرفیت، دسترسی، پاسخ نامعتبر و منبع ازقبل‌ساخته را بسنجد؛ نام/راز provider به مشتری نرسد.
- command جدید باید زمان‌بندی، قفل با مهلت متناسب و شاهد پیشرفت داشته باشد؛ heartbeat به‌تنهایی کافی نیست.
- authorization، CSRF/session و PageCache جداگانه بررسی شوند. حذف middleware برای سبزکردن تست مجاز نیست.
- migrationهای موجود و رابطه‌ها در تغییر جانبی دست نخورند. تغییر لازم schema/رابطه با migration جدید یا طرح صریح، بررسی سازگاری و مجوز مستقل انجام شود.
- تنظیمات واقعی در محل امن باقی بمانند؛ نمونهٔ config فاقد راز و با پیش‌فرض امن باشد.

## ۵. حداقل آزمون و تعریف پایان کار

پایان توسعه یعنی مسئله با تست رفتاری مربوط پوشش یافته، نتایج واقعاً اجراشده ثبت شده و مستند تغییر کرده است. پایان انتشار علاوه بر آن، نصب محدود و تأیید زندهٔ مصوب می‌خواهد.

| نوع تغییر | شواهد مورد انتظار |
|---|---|
| مستندات | تطبیق لینک‌ها و ادعاها، diff فقط مستند، مرز وضعیت تأییدشده/نامعلوم |
| PHP/backend | lint فایل‌های تغییرکرده، تست‌های مرتبط، بررسی مسیر خطا و قرارداد داده |
| UI/JS | آزمون منطق و مرورگر؛ fa/en/tr، فرم/نشست، موبایل و خطای console |
| مالی/تحویل | duplicate callback، timeout، retry، خطای provider، هم‌زمانی و عدم اثر واقعی روی حساب زنده در تست |
| دیتابیس | اجرای migration روی دیتابیس دورریختنی سازگار با تولید؛ بررسی rollback و داده موجود |
| Worker/n8n/infra | تست‌های همان جزء و بررسی سازگاری با API وب؛ استقرار و بازگشت مستقل |

همهٔ تست‌ها در checkout ایزوله اجرا شوند. صورتِ نتیجه شامل SHA، محیط، command، pass/fail/skip و محدودیت باشد. تست تاریخی یا screenshot قدیمی نتیجهٔ امروز نیست. تست روی SQLite به‌تنهایی سازگاری رفتار MariaDB تولید را اثبات نمی‌کند.

## ۶. قرارداد CI پیشنهادی؛ هنوز فعال نشده

در snapshot develop، مسیر `.github/workflows/` وجود نداشت؛ از این واقعیت دربارهٔ هر سرویس CI بیرونی نتیجه‌گیری نمی‌کنیم. تا ایجاد job واقعی و baseline معتبر، status check فرضی اجباری نشود.

مسیر مرحله‌ای:

1. CI بدون راز تولید و بدون deploy بسازید: checkout SHA صحیح، PHP 8.4 سازگار با lock، اکستنشن‌های `tests/bootstrap.php`، نصب وابستگی‌های قفل‌شده، lint و suite مرتبط. نتیجه‌های baseline ثبت شوند، نه اینکه skip شوند تا سبز دیده شوند.
2. تست JavaScript/Worker/n8n جدا گزارش شود. برای Vite ابتدا Node و lockfile اپ تثبیت و نصب تمیز بررسی شود؛ سپس `npm ci` و build به check معتبر تبدیل شوند.
3. با تأیید مالک، برای develop بازبینی لازم، جلوگیری از force-push/حذف و status checkهای واقعاً پایدار فعال شود. مسیر رفع اشکال اضطراری و بازبینی پس از آن هم تعریف شود.
4. انتشار تولید فقط با artifact/manifest مشخص، تأیید مسئول انتشار و دسترسی حداقلی به محیط مربوط انجام شود؛ push عادی به Git نباید به‌طور ضمنی عملیات مالی/زیرساخت اجرا کند.

در بررسی ۱۴ اکتبر، branch protection غیرفعال و فهرست rulesetها خالی بود. انتخاب `develop` به‌عنوان default در GitHub برای جلوگیری از اشتباه توصیه می‌شود، اما این سند آن تنظیم را تغییر نمی‌دهد.

## ۷. الگوی تحویل کار

```text
موضوع / شناسهٔ کار:
SHA مبنا و SHA نهایی:
base branch: develop
دامنه و فایل‌های تغییرکرده:
فایل‌ها و رفتارهای عمداً دست‌نخورده:
تست‌های اجراشده و نتیجه / موارد اجرا‌نشده:
اثر بر زبان / پول / schema / مجوز / job / provider:
مستند به‌روزشده:
انتشار لازم؟ مقصد و مسئول:
وضعیت: فقط Git / نصب‌شده / تأیید تولید / برگشت‌داده‌شده
طرح بازگشت و محدودیت آن:
```

مرجع خارجی برای تنظیمات حفاظتی، [مستند رسمی GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) است؛ سیاست بالا پیشنهاد ویژهٔ این پروژه است، نه گزارش اجرای آن.
