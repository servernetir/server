## نتیجهٔ بررسی طبیعی و علت باقی‌مانده

خواندن محدود وضعیت مالکِ متصل نشان داد `knowledge.internal.observed_at` در `2026-10-29T06:10:33Z` تازه شد؛ پنج منبع قبلاً موفق بودند و هنوز در فاصلهٔ شش‌ساعتهٔ خود قرار داشتند. منبع cPanel در `05:10:48Z` ناموفق ثبت شده و موفقیت قبلی نداشت. در `06:10:33Z` تنها ۳۵۸۵ ثانیه گذشته بود؛ شرط سخت ۳۶۰۰ ثانیه، آن را skipped کرد. بنابراین نبود incident تازه در آن نوبت، اثبات بهبود cPanel نبود.

این مشاهده از state موجود و فقط کلیدهای ثابت زمان/وضعیت گرفته شد. SQL write و HTTP در فرایند مشاهده مسدود، cache فرایند از نوع array و حمل‌ونقل اعلان‌ها ساختگی بودند. state مستقیماً خوانده شد؛ `Store::read()` که می‌تواند lock/permission ایجاد کند فراخوانی نشد. شناسهٔ مالک، مشتری، متن حافظه و کلید رمز در خروجی نبودند. تلاش نخستِ مشاهده به‌علت نصب guard پیش از ثبت providerها متوقف شد؛ پس از اصلاح ترتیب، مشاهده موفق شد. این خطا به معنی شکست نصب دو فرمان نبود.

دریافت محدود همان URL رسمی با Guzzle و cURL مستقل، با تأیید peer/hostname روشن، هر دو پیش از دریافت HTTP شکست خوردند: `errno=60`، `ssl_verify_result=18`، `http_status=0` و صفر بایت بدنه. خطا در مرحلهٔ ارتباط/TLS است؛ ۴۰۴ یا XML خراب از این شواهد نتیجه نمی‌شود. [راهنمای رسمی cPanel](https://support.cpanel.net/hc/en-us/articles/360053124534-Where-can-I-locate-the-cPanel-changelogs) همان URL تنظیم‌شدهٔ `https://docs.cpanel.net/release-notes/release-notes/index.xml` را معرفی می‌کند؛ URL تغییر نکرد. منشأ ارائه‌شدن زنجیرهٔ نامعتبر در مسیر خروجی سرور، از این داده‌ها روشن نشده و نیازمند بررسی DNS/زنجیرهٔ گواهی میزبان است. هیچ استثنای verify=false یا اعتماد به گواهی ناشناخته اضافه نشد.
