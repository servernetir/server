## رفتار

در جدول سرویس‌های زنده و بخش جمع‌شوندهٔ سرویس‌های خاتمه‌یافته، ستون «زیرساخت و رهگیری» اضافه شد. نام واقعی، شناسهٔ مبدا و مکان از رابطه‌های موجود خوانده می‌شوند. نمونهٔ واقعی تحویل‌شده بر پلن سفارش مقدم است؛ شناسهٔ پلن هرگز به عنوان شناسهٔ سرور استفاده نمی‌شود. هاست‌های موجود نام سرور تحویل، vendor ثبت‌شده و پنل WHM/Plesk/DirectAdmin همان سرور را نشان می‌دهند. سرویس فاقد اطلاعات، «ثبت نشده» دارد؛ زیرساخت از نام/IP حدس زده نمی‌شود.

| زیرساخت | مقصد |
| --- | --- |
| ArvanCloud | صفحهٔ جزئیات ابرک با منطقه و ID موجود در provider_ref |
| Aeza | صفحهٔ سرویس برای ID عددی؛ order:* فقط پنل فهرست، چون هنوز سرور نیست |
| SaladCloud | گروه همان سازمان/پروژهٔ تنظیم‌شده و نام گروه ثبت‌شده |
| Hetzner Cloud | کنسول Cloud همراه شناسهٔ سرور؛ project ID در دادهٔ فعلی موجود نیست و لینک دقیق حدس زده نمی‌شود |
| Hetzner Robot | پنل Robot مستقل از Cloud، همراه شناسهٔ منبع |
| OVH / LightNode | پنل رسمی همراه شناسهٔ ثبت‌شده |
| Proxmox | مبدا پنل از تنظیم API، بدون مسیر API، query یا اعتبارنامه |
| هاست | پنل سرور تحویل با پورت ثبت‌شده؛ URL دارای user/password/query/fragment رد می‌شود |

لینک خارجی در تب تازه با noopener/noreferrer و بدون referrer باز می‌شود. هیچ API زیرساختی برای نمایش این داده فراخوانی نمی‌شود. eager-load موجود services.server/cloudPlan/cloudInstance حفظ شده و رابطه، migration و فیلدهای hidden مدل تغییر نکرده‌اند. اطلاعات تنها در view داخلی پشت گیت staff استفاده می‌شوند؛ پنل/JSON مشتری سفیدبرچسب می‌ماند.

دکمهٔ «ثبت تیکت برای این مشتری» بالای پرونده، فرم همان صفحه را باز می‌کند. گیرنده با customer_ids[] به مشتری جاری محدود شده؛ موضوع، بخش، اولویت و پیام وارد می‌شوند. فرم از مسیر موجود /admin/tickets/create و StaffTicketCreator استفاده می‌کند؛ پیام با نقش staff، اعلان قبلی و انتقال به گفتگو حفظ‌اند. خطای اعتبارسنجی، پیش‌نویس و فرم باز را نگه می‌دارد و فرم فروش را باز نمی‌کند. صرف بازدید صفحه هیچ تیکت یا اعلانی نمی‌سازد.

## دامنه و آزمون

چهار فایل تولید: view مشتری، دو partial و `app/Support/AdminServiceInfrastructure.php`. یک فایل تست تازه نیز اضافه شد. مرجع دقیق فایل‌ها و هش بایت‌ها در [manifest انتشار](customer-profile-2026-10-25/release-manifest.json) است.

- ۴۶ تست و ۵۴۴ assertion موفق، PHP 8.4.26 و SQLite حافظه‌ای در checkout ایزوله.
- مجموعه: AdminCustomerInfrastructureAndTicketTest، AdminCustomerServiceTableTest، AdminCustomerTest، AdminTicketCreateTest و CustomerAccountBanTest.
- lint PHP و قالب‌بندی Pint فایل‌های PHP تازه موفق؛ git diff --check بدون خطا.
- آزمون دسترسی نقش author، گیرندهٔ ثابت، نویسندهٔ پیام staff، حفظ draft، عدم ارسال در GET، سرویس لغوشده، تقدم نمونه بر پلن، تفکیک Cloud/Robot و URL فاقد راز پوشش داده شد.
- در تست‌ها Mail/HTTP ساختگی‌اند؛ تیکت یا اعلان واقعی برای مشتری ارسال نشد.
- ساختار URLهای Arvan/Aeza/Salad با router منتشرشدهٔ فعلی خود سرویس‌دهنده تطبیق داده شد؛ ورود و مشاهدهٔ واقعی منابع در پنل‌های مبدا انجام نشده است.
- مدیریت در این اپ مسیر فارسی داخلی دارد؛ تغییری در صفحات عمومی fa/en/tr داده نشده است.
- در مرحله ۲۵ اکتبر، مرور تصویری و پذیرش نشست واقعی مدیر انجام نشده بودند. پذیرش تولید و دسکتاپ در ۲۶ اکتبر طبق گزارش بالا تکمیل شد؛ موبایل، ارسال واقعی تیکت و مجموعه کامل پروژه همچنان اجرا نشده‌اند.

## انتشار و بازگشت

مراحل زیر **انجام نشده‌اند** و بازگشتِ واقعی لازم نشده است:

۱. HEAD تازهٔ develop و هش view زنده دوباره کنترل شود. manifest فعلی مربوط به snapshot این بررسی است؛ در اختلاف، ادغام و تست دوباره لازم است.
۲. با قفل مشترک `.servernet-web-release.lock` و پشتیبان خصوصی، ابتدا helper و partialها و در پایان view نصب شوند. هیچ endpoint عمومی موقت، تغییر .env، migration، cron یا flush سراسری لازم نیست.
۳. lint و کامپایل Blade با short_open_tag تولید و بررسی هش فایل‌های نصب‌شده انجام شود؛ در نشست مجاز، ستون زیرساخت و بازشدن فرم مشتری بدون ارسال تیکت بررسی شوند.
۴. در شکست پذیرش، view با کنترل هش به نسخهٔ پشتیبان همین انتشار برگردد. فایل‌های تازهٔ بدون استفاده می‌توانند باقی بمانند؛ تغییر جدیدتر همکار بازنویسی نشود.

تغییر شبکه، route/NAT/firewall، DNS، VM، خرید/حذف منبع، دادهٔ مالی یا تنظیمات پیام‌رسان در این کار وجود ندارد.
