### قاعدهٔ حل اختلاف اسناد

برای رفتار کد، فایل همان SHA معتبر است؛ برای وضعیت محیط، شاهد تازه و مجاز همان محیط لازم است. گزارش «منتشر شد» فقط دربارهٔ تغییر و زمان خودش گواه است. استانداردهای این مجموعه، نصب یک کنترل یا سیاست GitHub را اثبات نمی‌کنند. در تعارض، اختلاف را ثبت و بررسی کنید؛ نه اینکه یکی از نسخه‌ها را کورکورانه روی دیگری نصب کنید.

## ۱. محصول و معماری سطح بالا

سرورنت یک سایت صرفاً معرفی خدمات نیست؛ در یک اپ Laravel، کاتالوگ، سفارش، کیف پول/پرداخت/صورتحساب، تحویل، چرخهٔ سرویس و دامنه، پشتیبانی، محتوای چندزبانه و اتصال به زیرساخت‌ها را مدیریت می‌کند.

```text
مهمان / مشتری / کارمند
        |
        +-- servernet.cloud                سایت عمومی fa/en/tr
        +-- console.servernet.cloud        پنل مشتری و مدیریت
                       |
             middleware / routes / Blade
                       |
                website/  (Laravel)
                 |       |       |
        داده و مالی   زمان‌بندی   اتصال‌های بیرونی
                 |       |       |
     MariaDB تولید*   تحویل/تمدید  Cloud / Domain / Payment / Notify / AI
     SQLite محلی         |                      |
                         |       +--------------+----------------+
                         |       |              |                |
                     scheduler  providerها    relay/n8n     Cloudflare Worker
                                 |
                              Proxmox
                                 |
                infra/ansible و عامل‌های desired-state شبکه
```

`*` MariaDB و چیدمان میزبان از راهنمای فنی/گزارش‌های قبلی آمده‌اند؛ در این بازنگری زنده سنجیده نشده‌اند. نمودار اتصال منطقی است، نه نقشهٔ تأییدشدهٔ همهٔ ماشین‌ها، IPها یا سرویس‌های شبکه.

## ۲. محیط‌ها و مالکیت فایل

## ۳. نقشهٔ حوزه‌های کد

مسیرها نسبت به ریشهٔ مخزن هستند. وجود پوشه یا driver نشانهٔ پیاده‌سازی/اتصال در مخزن است؛ به معنی آماده‌بودن تمام قابلیت‌ها در تولید نیست.

### Registry زیرساخت ابری

در [CloudManager](../../website/app/Services/Cloud/CloudManager.php)، این هشت کلید ثبت‌اند: `hetzner`، `aeza`، `arvan`، `ovh`، `proxmox`، `salad`، `hetzner-robot`، `lightnode`.

`hetzner` و `hetzner-robot` عمداً API و اعتبارنامهٔ جدا دارند. `configured()` از `isConfigured()` استفاده می‌کند؛ پس «driver موجود است» با «حساب تنظیم شده»، «ظرفیت موجود» و «تحویل سالم» چهار ادعای متفاوت است. `label()` خروجی مشتری و `realLabel()` خروجی داخلی مدیر را جدا می‌کنند.

## ۴. جریان‌های حساس

### سفارش، پول و تحویل

راهنمای موجود مسیر سفارش/فاکتور/تأیید پرداخت/صف تحویل را ثبت کرده است. تماس provider در پاسخ مرورگر نباید جای ثبت وضعیت پایدار و پردازش قابل پیگیری را بگیرد. برای timeout باید وجود منبع قبلی بررسی شود؛ تلاش مجدد کور می‌تواند هزینهٔ دوم بسازد. وضعیت پرداخت، provisioning، instance و آماده‌بودن محصول را جدا بررسی کنید.

GPU علاوه بر تحویل، صف درخواست ظرفیتِ بدون پرداخت دارد؛ گزارش‌های ۱۴ اکتبر و فرمان‌های `cloud:advance-gpu-capacity` و `cloud:recover-gpu-delivery` این تفکیک را نشان می‌دهند. روایت قدیمی «همهٔ درخواست‌ها ابتدا پول می‌گیرند» را به تمام مسیرها تعمیم ندهید. برای قانون اعتبار شروع، مرجع تغییر بعدی باید هم کد، هم آزمون مرزی و هم متن سه‌زبانهٔ شرایط باشد؛ این مستندسازی سیاست مالی را عوض نمی‌کند.

### اعلان

رویداد کسب‌وکار به اعلان مشتری/مدیر و سپس کانال می‌رود. کاتالوگ، متغیرهای template و registry پیامک باید هم‌نسخه باشند. [گزارش تازهٔ اعلان‌ها](../../NOTIFICATION-CATALOG-2026-10-14.md) برای سابقهٔ reconciliation مفید است؛ شمارنده‌های قدیمی راهنما را وضعیت روز ندانید.

در مسیر SMS، میان README قدیمی n8n و راهنمای فنی جدید اختلاف معماری وجود دارد. وضعیت sender/config/workflow فعال باید قبل از تغییر یا حذف رله تطبیق داده شود؛ هیچ‌یک از این اسناد مجوز ارسال پیام واقعی برای آزمایش نیست.

### زیرساخت جدا از وب

[infra](../../infra/README.md) عملیات Proxmox، قالب VM، مسیریابی کشور و عامل‌های pull را توضیح می‌دهد. کد `bootstrap/app.php` مسیرهای agent و احراز آن‌ها را نیز لحاظ کرده است. برنامهٔ قدیمی مراحل feature در README زیرساخت، به‌تنهایی وضعیت استقرار امروز نیست. نسخهٔ کد وب، Worker، n8n و عامل میزبان باید در یک release record مرتبط شوند ولی مستقل قابل بازگشت باشند.

## ۵. زمان‌بندی و سلامت

منبع ثبت زمان‌بندی در کد [routes/console.php](../../website/routes/console.php) است. موارد زیر نمونه‌های مهمِ بخش‌های خوانده‌شده‌اند، نه فهرست کامل تمام jobها یا گواه نصب crontab:

| کار | تناوب ثبت‌شده |
|---|---|
| `provision:run`، بازیابی تحویل GPU و پیشبرد ظرفیت GPU | هر دقیقه |
| `provision:verify-failed` | هر پنج دقیقه |
| `domains:provision` و `domains:renew` | هر دقیقه |
| `services:renew-due` / `services:lifecycle` | پانزده دقیقه / پنج دقیقه |
| `bale:work` و `crypto:watch` | هر دقیقه |
| `snapppay:reconcile` | هر پنج دقیقه |
| `ai:reconcile` / `ai:recover-usage` | دقیقه / پنج دقیقه؛ بازیابی late نیز جدا ثبت است |
| کاتالوگ‌های Storage / object-gateway lifecycle | شش ساعت / ساعتی |
| heartbeat فایل / `system:health` | دقیقه / پانزده دقیقه |

سلامت پیشنهادی چهار لایه دارد: HTTP و boot؛ سلامت داده/کش؛ سن و پیشرفت صف‌ها؛ و نتیجهٔ واقعی provider/مصرف. heartbeat تنها زنده‌بودن یک مسیر را نشان می‌دهد. صفر بودن طول صف نیز اگر enqueue شکسته باشد گواه سلامت نیست.

برای هر job، نام، مالک، زمان آخرین شروع/موفقیت، مدت اجرا، سن قدیمی‌ترین کار، تعداد retry، قفل و مسیر خطا ثبت شود. تعیین آستانهٔ عددی هشدار باید با زمان طبیعی آن job و هزینهٔ شکست انجام شود؛ این آستانه‌ها در این بازنگری اندازه‌گیری نشده‌اند.

## ۶. مرز امنیتی و داده

کد bootstrap نقش admin/staff و توکن API پشتیبانی را تفکیک می‌کند. PageCache داخل گروه web قرار گرفته تا قرارداد نشست/CSRF حفظ شود. trusted proxyها محدود به رنج‌های ثبت‌شدهٔ Cloudflare هستند؛ اعتماد عمومی به همهٔ proxyها جایگزین این طراحی نیست.

endpointهای مستثنا از CSRF همچنان احراز جایگزین می‌خواهند. مسیرهای deploy، پرداخت، agent و webhook را با درخواست آزمایشیِ اثرگذار بررسی نکنید. جزئیات هر کنترل باید همراه handler و تستش بازبینی شود؛ مشاهدهٔ alias به معنی اثبات امنیت همهٔ endpointها نیست.

فهرست host/IP، اسرار، backup و دادهٔ مشتری در مخزن عمومی نگهداری نشوند. برای inventory عملیاتی از شناسهٔ داخلی و محل امنِ دسترسی استفاده کنید. RPO/RTO، retention، آزمون restore و roster مسئولان هنوز نیازمند ثبتِ تأییدشده‌اند.

## ۷. نگهداری این نقشه
