# اتصال مدیریتی ServerNet به هوش مصنوعی — ۲۱ نوامبر ۲۰۲۶

وضعیت این نسخه: کاندید توسعه؛ نصب تولید، ثبت افزونه در حساب ChatGPT و اتصال SSH هنوز تأیید نشده‌اند. اجازه مالک: ابتدا اتصال شخصی مدیریتی، سپس برنامه جدا برای MCP مشتریان با تفکیک دسترسی.

## مقصد و کشف OAuth

برای مرحله اول از TLS/DNS موجود کنسول استفاده می‌شود؛ `mcp.servernet.cloud` صرفاً پیشنهاد اولیه بوده و ساخته نشده است.

| مورد | نشانی/مقدار |
|---|---|
| MCP، Streamable HTTP | `https://console.servernet.cloud/api/mcp/admin` |
| تنظیمات | `/admin/mcp` |
| protected resource | `/.well-known/oauth-protected-resource/api/mcp/admin` |
| authorization metadata | `/.well-known/oauth-authorization-server` |
| ورود و تأیید | `/admin/mcp/oauth/authorize` |
| token | `/api/mcp/oauth/token` |
| ثبت خودکار DCR | `/api/mcp/oauth/register` |
| روش token endpoint | public client / `none` با PKCE S256 |
| scope پایه | `infrastructure:read` |
| scope اختیاری دستور | `infrastructure:execute` |

OAuth از Laravel Passport/League و انتقال MCP از Laravel MCP استفاده می‌کند. کلاینت DCR فقط نشانی بازگشت HTTPS دقیق ChatGPT را می‌پذیرد؛ نام کلاینت مجوز محسوب نمی‌شود. CIMD و OIDC در این نسخه ادعا یا تبلیغ نمی‌شوند. هیچ client secret ساختگی لازم نیست. `resource` در authorize و token کنترل می‌شود؛ JWT امضاشده issuer و audience مخصوص MCP دارد و در درخواست دوباره بررسی می‌شود.

## مرزهای دسترسی

- `users` مدیر و `customers` مشتری مستقل می‌مانند. guard تازه `mcp_admin` است؛ ورود نشست به‌تنهایی توکن MCP نیست. نقش مدیر، شناسه مالک تعیین‌شده در نصب و فهرست اجازه در **هر درخواست** دوباره بررسی می‌شوند. مدیر دیگر نمی‌تواند خود را از رابط ثبت کند.
- `mcp_admin_enabled` پیش‌فرض خاموش است. `mcp_admin_owner_user_id` هنگام نصب به شناسه مدیر صریح وصل می‌شود. فعال‌سازی برای حساب و هر OAuth consent مرحله انسانی مستقل‌اند. شناسه/نام/کلید واقعی در مخزن قرار نمی‌گیرد.
- توکن یک‌ساعته و refresh چرخشی ۳۰روزه است. لغو اتصال همه توکن‌ها/refreshهای همان کاربر و کلاینت را باطل و دستورهای معلق آن اتصال را لغو می‌کند. هیچ رمز یا کلید زیرساخت به کلاینت برگردانده نمی‌شود.
- مشاهده فهرست به معنی سلامت اتصال نیست. WHM/Plesk با client موجود، و Proxmox با GET محدود و TLS معتبر آزموده می‌شوند. استثنای قدیمی TLS به مسیر MCP منتقل نشده است؛ خطای گواهی نیازمند اصلاح/CA معتبر است.
- سه ابزار خواندنی: `infrastructure_inventory`، `infrastructure_status` و `ssh_diagnostic`. scope اجرای دستور دو ابزار اضافه می‌کند: `request_ssh_command` و `execute_ssh_command`.
- دستور آزاد فقط پس از مشاهده و تأیید متن دقیق روی پنل همان مالک، برای همان OAuth token، مقصد، کلید میزبان و هویت SSH، تا ۱۰ دقیقه معتبر است. claim پایدار قبل از تماس شبکه ثبت می‌شود. پاسخ نامعلوم/اجرای قطع‌شده تکرار خودکار ندارد. محتوای دستور و نتیجه در DB رمزگذاری می‌شوند؛ لاگ عمومی فقط شناسه ابزار/مالک و نتیجه کلی دارد.

## SSH: مرحله مستقل راه‌اندازی

رجیستری خصوصی `mcp_admin.ssh_registry` خارج webroot قرار می‌گیرد. نمونه ساختار، بدون داده واقعی:

```json
{
  "proxmox-ir": {
    "label": "Proxmox Iran",
    "host": "management.example.invalid",
    "port": 22,
    "user": "mcp-ops",
    "identity_file": "/private/mcp/proxmox-ir.key",
    "known_hosts_file": "/private/mcp/known_hosts"
  }
}
```

پوشه 0700، رجیستری/کلید/known_hosts همگی 0600؛ دو فایل کلید و known_hosts باید داخل همان پوشه خصوصی رجیستری باشند. مقصد/کاربر/پورت از ابزار پذیرفته نمی‌شوند. کلید هر مقصد جدا، حساب سیستم‌عامل با حداقل مجوز و sudo محدود، `from=` محدود به واسط و گزینه‌های `restrict` توصیه می‌شوند. root نامحدود روی وب‌اپ عمومی پیش‌فرض این طرح نیست؛ برای دسترسی کامل root، واسط اجرایی جدا و بررسی دامنه لازم است.

کلید میزبان باید از کنسول مورداعتماد یا مسیر مستقل تأیید شود؛ `ssh-keyscan` به‌تنهایی اثبات هویت نیست. اجرای SSH با BatchMode، IdentitiesOnly، عدم forwarding و StrictHostKeyChecking انجام می‌شود. عیب‌یابی‌های ثابت فقط uptime، df، free و systemctl --failed هستند. خروجی محدود و برای الگوهای معمول راز پالایش می‌شود؛ این پالایش تضمین حذف همه رازهای ممکن نیست. ابزار خواندن/استخراج اعتبارنامه ارائه نمی‌شود. Plesk ویندوز برای API نیازی به فعال‌سازی OpenSSH ندارد؛ SSH ویندوز بدون بررسی جدا آماده اعلام نمی‌شود.

## وابستگی‌ها و سازگاری

در پیش‌بررسی تولید، framework و Guzzle و http-foundation از develop جدیدتر بودند. کاندید با نسخه‌های اصلاح‌شده هم‌راستا شد: Laravel 13.43.0، Guzzle 8.5.4، Symfony http-foundation 8.1.11. Composer audit کاندید صفر advisory گزارش کرد. بسته انتشار هرگونه حذف/downgrade وابستگی runtime موجود را رد می‌کند؛ lock قدیمی روی سرور کپی نمی‌شود. تغییر نسخه‌های مرتبط به معنی پذیرش کل اپ نیست.

آزمون PHP 8.4.27/SQLite: ۲۴ آزمون اختصاصی با ۱۲۵ بررسی موفق. با آزمون‌های مرتبط ورود/نقش/نشست/Studio/API مشتری، ۱۲۸ اجرا، ۱۲۷ موفق و یک شکست قدیمی Studio در `test_ai_cost_is_still_settled_by_the_existing_gateway` ثبت شد. همان شکست روی checkout پایه مستقل با وابستگی‌های پایه نیز تکرار شد. مجموعه نهایی پس از آخرین تغییر و CI جدا ثبت می‌شود. MariaDB محلی راه افتاد اما اتصال تست با محدودیت شبکه محیط رد شد؛ آن پذیرش محلی ادعا نمی‌شود. workflow اختصاصی SQLite/MariaDB بدون راز تولید اضافه شده است.

## انتشار و بازگشت

`scripts/admin-mcp-release-20261121.json` فهرست دقیق ۴۱ فایل اپ و پنج migration جدید است. فایل‌های پرتعارض با patch زمینه‌دار روی نسخه زنده آماده می‌شوند؛ اختلاف‌های دیگر تولید حفظ می‌شوند. `scripts/deploy-admin-mcp-20261121.py` سه مرحله prepare/apply/verify دارد. SHA ثابت develop و شناسه صریح مالک لازم‌اند. prepare فقط فایل خصوصی و vendor قفل‌شده می‌سازد. apply پس از hash guard، با قفل، پشتیبان خصوصی و کنترل نبود downgrade نصب می‌کند. فقط پنج migration همین بسته اجرا می‌شوند؛ migrate عمومی/صف/کرون/خرید/حذف/پیامک اجرا نمی‌شوند.

وابستگی‌ها در محل خصوصی از lock با no-dev/no-scripts/no-plugins ساخته و platform بررسی می‌شوند. `.env`، webroot و داده مشتری کپی نمی‌شوند. cache تنظیمات زنده با حفظ مقادیر قبلی فقط برای guard/config تازه به‌روز می‌شود؛ کش اشتراکی flush نمی‌شود. route cache موجود نیاز به طرح مستقل دارد و نصب را متوقف می‌کند. کلید امضای موجود هرگز چرخانده نمی‌شود. پرچم دسترسی روشن نمی‌شود و authorized_keys هیچ میزبانی تغییر نمی‌کند.

بازگشت فایل/vendor و cache از پشتیبان همین packet و با hash guard انجام می‌شود؛ جدول‌های افزایشی و کلید امضا حذف نمی‌شوند. قطع OAuth از پنل فوری است. پس از صدور توکن یا اجرای دستور، برگشت کد اثر بیرونی/داده را برنمی‌گرداند. تغییر چندفایلی یا جابه‌جایی vendor اتمی سراسری نیست؛ انتشار باید پنجره و پذیرش مستقل داشته باشد.

## مرحله بعد: MCP مشتریان

در این انتشار **فعال نیست**. پیش از عرضه:

1. resource، guard، OAuth clients، scopeها و صفحه consent مشتری از مدیر جدا شوند؛ هیچ proxy عمومی به ابزارهای admin/SSH اضافه نشود.
2. هر ابزار هویت را از توکن بگیرد و تمام service/job/domain IDها را با مالک همان حساب دوباره تطبیق دهد؛ شناسه حساب از آرگومان مدل مرجع اعتماد نیست.
3. امکانات از API رسمی مشتری و همان سرویس‌های صورتحساب/کیف پول استفاده کنند؛ توکن جدید مسیر ارزان‌تر یا bypass مالی ایجاد نکند. scope محصول، سقف هزینه/روزانه، انقضا و Idempotency-Key روی عملیات پولی لازم‌اند.
4. ابتدا خواندن سرویس/موجودی/مصرف، سپس start/stop مجاز و در نهایت سفارش/تمدید با پیش‌نمایش مبلغ و تأیید. حذف، بازسازی، تغییر رمز، برداشت و export رازها سیاست مستقل و تأیید قوی می‌خواهند.
5. هر کاربر اتصال‌ها، مجوزها و تاریخچه خودش را ببیند و لغو کند؛ نشت متقاطع با ID یکسان بین جدول‌ها، توکن دزدیده‌شده، scope escalation، retry و هم‌زمانی روی SQLite/MariaDB آزموده شود.

همه مشتریان می‌توانند از یک endpoint مشترک با هویت و grant جدا استفاده کنند؛ لازم نیست برای هر مشتری سرور یا کلید مدیریتی مستقل عمومی ساخته شود. نشانی عمومی آن مرحله پس از پیاده‌سازی و آزمون تعیین می‌شود.
