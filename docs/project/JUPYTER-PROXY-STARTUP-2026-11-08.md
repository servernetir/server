# راه‌اندازی افزونهٔ پروکسی پیش از Jupyter

وضعیت: کاندید آماده و آزموده‌شدهٔ محلی؛ روی سرویس تولید نصب یا تأیید نشده است.
شاخهٔ مبنا: `develop` در `17a3c89eeaebeb522e4a37995388ee0de0b9cf07`.

## مسئله و تغییر محدود

نصب افزونه پس از شروع Jupyter، handler پروکسی را به فرایند در حال اجرا اضافه
نمی‌کند. فایل `relay/jupyter/startup-command.json` برای تصویر ثابت‌شدهٔ Docker
Stacks، نصب نسخهٔ مشخص افزونه و ثبت آن را پیش از اجرای launcher اصلی انجام
می‌دهد. نسخهٔ مطابق دوباره نصب نمی‌شود؛ شکست نصب یا ثبت، اجرای Jupyter را
متوقف می‌کند تا آماده‌بودنِ ناقص پنهان نشود. تنظیمات احراز، شبکه و کاربر از محیط
موجود به launcher می‌رسند. هیچ مدل OCR نصب نمی‌شود.

این فایل به کارخانهٔ سرویس متصل نشده و عرضهٔ سراسری را تغییر نمی‌دهد. ابتدا
باید روی یک deployment مجاز، با ثبت تنظیمات قبلی و طرح بازگشت، ارزیابی شود.
کد Worker، relay، صورتحساب، دادهٔ مشتری و فرایندهای سرویس تولید تغییر نکرده‌اند.

## شواهد محلی ۸ نوامبر ۲۰۲۶

محیط مجزا: Python `3.12.14`، Jupyter Server `2.21.1`،
Jupyter Server Proxy `4.6.0` و Tornado `6.6`.

دستور اجرا، در virtual environment دورریختنی:

```sh
python relay/jupyter/test_startup.py
```

پنج آزمون واقعی HTTP در حدود پنج ثانیه موفق شدند:

1. افزونهٔ نصب‌شده اما بارگذاری‌نشده، مسیر پروکسی را ۴۰۴ می‌دهد؛ پس از فرمان
   آماده‌سازی و آغاز فرایند تازه، GET همان مسیر به برنامهٔ داخلی ۲۰۰ می‌دهد.
2. POST حاوی JSON فارسی فقط با هدر احراز، بدون کوکی یا توکن در URL، عبور می‌کند.
3. توکن نامعتبر پیش از رسیدن به برنامه رد می‌شود.
4. پاسخ ۴۰۴ واقعی خود برنامه حفظ می‌شود؛ خطا به موفقیت ظاهری تبدیل نمی‌شود.
5. متغیرهای موجود احراز و `NOTEBOOK_ARGS` به launcher می‌رسند.

آزمون از Jupyter واقعی و launcher محلیِ جایگزین استفاده می‌کند. entrypoint و
فایل‌سیستم تصویر CUDA، نسخهٔ Python آن تصویر، GPU، HTTPS عمومی، Worker/relay و
هزینهٔ واقعی را نمی‌سنجد. خروجی محلی، رفع مشکل سرویس اصلی نیست. فرایندها و
فایل‌های موقت آزمون پس از پایان جمع می‌شوند؛ هزینهٔ زیرساخت GPU در این آزمون صفر است.

## پذیرش زندهٔ باقی‌مانده

- هویت deployment، وضعیت واقعی instanceها و تنظیمات فعلی پیش از هر تغییر خوانده
  شوند؛ وضعیت تجاری «فعال» جای runtime را نمی‌گیرد.
- وضعیت فایل‌ها/پشتیبان مستقل و اثر تغییر command یا ایجاد مجدد محیط بررسی
  شود؛ حفظ داده در stop/start تضمین نشود.
- پیش از روشن‌کردن، مجوز مشتری، نرخ، سقف زمان/هزینه و زمان پایانِ زودتر از سقف
  ثبت شود. آماده‌سازی در حالت خاموش انجام شود.
- پس از ارزیابی entrypoint همان تصویر، command کاندید فقط در محدودهٔ مصوب
  اعمال شود؛ فرایند اصلی Jupyter با kill یا stop دستی خاتمه داده نشود.
- GET و POST از نشانی اصلی HTTPS بدون نشست و بدون راز در URL، رد دسترسی
  نامعتبر، محدودیت مؤثر بدنه و timeout همهٔ لایه‌ها سنجیده شوند.
- پس از پایان آزمون یا رسیدن به سقف، توقف از مسیر مدیریت سرویس درخواست و
  وضعیت نهایی تمام instanceها تأیید شود؛ زمان و ریز کارکرد واقعی گزارش شود.
- مجوز مصرف به معنی مجوز نصب مدل، پردازش اسناد یا ادامهٔ بیشتر از سقف نیست.
