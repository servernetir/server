## Behavior

- New selector `USDT_BEP20` persists ticker USDT, chain bsc, network BEP20. Existing USDT selector remains TRON. Returning to/reissuing a payment preserves its chain. BEP20 is listed first when its pool exists; existing payment visibility by language remains authoritative.
- Existing atomic wallet claim, 59-minute stablecoin window, release and configured cooldown are reused. Production was observed with 5 TRON wallets and a **one-hour** effective cooldown. The five new wallets are a separate pool, supporting up to five concurrent reservations; cooldown still limits throughput after release.
- The fixed BSC token contract is `0x55d398326f99059ff775485246999027b3197955`. The watcher validates chain ID 56, token decimals 18, economic-finality head, recipient Transfer logs, successful receipt, canonical block hash and timestamp. Removed logs, failed transactions, wrong destination/contract, wrong chain and integer overflow cannot credit invoices.
- Existing database BIGINT values use integer **micro-USDT (6 accounting decimals)**. EVM uint256 amounts are converted from 18 decimals with decimal-string arithmetic and rounded DOWN below one micro-USDT. No schema or old migration is changed. No new runtime dependency or spending/signing capability is added.
- The existing minute `crypto:watch` dispatches by chain. RPC failure does not settle or expire the failed chain in that sweep. Existing `(chain, txid)` and normal PaymentService settlement are retained.
- Historical `crypto:audit` remains explicitly TRON-only. It does not misquery BSC transaction hashes against TronGrid. A historical BSC audit is outside this addition; current BSC receipts are checked before settlement.

## Release

`python3 scripts/bep20-release/deploy.py prepare|install|verify|cleanup <pinned-commit>` uses both shared release locks, exact baseline/source guards, private backup and PHP/Blade lint. It installs eight source files and only three compiled templates. An authenticated admin+CSRF activation helper invalidates only those bytecode files and is removed after acceptance. No global cache clear, environment edit, migration, schema change, extra scheduler or wallet movement.

Five wallets must only be added after code/bytecode acceptance through the existing admin pool form, network bsc, in the owner's supplied order. Never add them as manual/offline accounts.

Rollback: disable new BSC pool addresses through admin to stop new reservations, retain pending records, restore only manifest files under the same guards, refresh their web bytecode; preserve all payment and wallet history. Do not roll back while BSC payments are open without a separate reconciliation plan. The script's rollback mode restores code only and refuses later file drift; it does not alter financial data.
