# Cloud SMS: integration candidate

Base: develop at 12e98f06b9d6280464b226085b3d053bd95a1ac2.

## Scope

Three locale-aware public plans at `/cloud/sms`, customer workspace at
`/account/sms`, and owner-only controls at `/admin/sms`. This uses the existing
service, invoice, payment settlement, renewal and provisioning infrastructure.
The OTP sender and its keys are unchanged.

Config is the sole plan-price source: annual access 0/249000/599000 IRT;
renewal 0/129000/299000 IRT; proposed Persian base-segment rates
2290/2090/1990 IRR. Quotes preserve the selected ACL and pricing evidence.
The declared native minimum credit is 1000000 IRR, purchased separately.
The company wallet never transfers or subtracts SMS sending credit here.

## Default state and limits

Sales and automation are OFF. No production schema, key, reseller package,
gateway, DNS or financial operation is changed by committing this code.

Opening sales requires an independent reseller API key, the exact parent ID,
three ACL IDs, verified native tariffs, complete per-segment cost, access-fee
tax configuration and evidence for commercial terms, native credit/profit
settlement and unattended API access. Evidence expires in at most seven days.
The preflight only reads packages/balance and NEVER enables sales.

The branded login destination is `https://sms.servernet.cloud`; its DNS and SSL
must be established without changing apex nameservers or breaking existing .ir
SMS relay infrastructure. Existing provider accounts and gateway assignments
are not silently changed.

Native recharge, sender purchase, documents, pattern approval and initial
password recovery are performed in the provider-hosted branded panel.
We do not promise SSO, automatic top-up of the parent account, wallet-transfer
APIs, line quotas, delivery guarantees or an implemented provider-profit feed.
These require separate official contracts and verified capabilities.

## Safety properties

Identity and initial random password are encrypted on the new model and hidden
from serialization. Identity consent is timestamped. Customer forms use the
existing customer auth/active/IP and privacy middleware. Admin routes require
the staff guard and admin middleware; customer credentials never grant access.
Requests only use the fixed official Edge origin, with redirects disabled.
Keys, bodies and upstream validation messages are not logged.

User creation returns data=null in the current official contract. Intent is
stored before POST; retries read the exact username and require parent ID,
national ID, mobile and the order-specific marker before binding the account.
Unknown creation is never blindly repeated. HTTP success alone is insufficient:
ACL, expiry, identity and provider review flags must match before activation.

Upgrade invoices deliberately have no service_id: the ordinary settlement
must not extend the annual access period. Renewal invoices remain on the
existing service, whose recurring price is the renewal price. The free tier
uses an automatically extended zero-fee access period without a payment entry.
Suspension/release closes access and retains the upstream account and credit.
No destructive delete endpoint is implemented.

## Tests and deployment

The new Cloud SMS CI installs locked dependencies without application scripts,
lints PHP, runs the isolated SMS/Store suites with fake providers and checks
GSM/UTF-16 segmentation. CI results are the test receipt; this file does not
claim a live transaction or production delivery.

Deploy only a reviewed file manifest with hashes and concurrency checks per
DEPLOYMENT.md. Install the new schema only in an explicitly authorized data
step; do not run unrelated pending migrations or broad seeders. New tables
remain after rollback: disable flags, restore reviewed files and reconcile
any already-created provider accounts instead of dropping customer records.

The existing Laravel scheduler gains `sms:sync-subscriptions`; no new host
cron or `schedule:run` test is required. Default flags ensure the job is inert.
Before live activation verify account creation/reconciliation, ownership,
native payment and profit, credit retention, expiry semantics, access restore
and the branded login. Real SMS/payment tests need the named test account,
recipient and a spending limit; no such real operation was executed here.
