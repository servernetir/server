# Existing backup account: verified suspension and payment restoration

The existing application flow handles billing restoration without a new automation. A pending billing-origin manual suspension must remain pending until the provider change is verified. The existing admin acknowledgment then records `billing_suspend.confirmed_at` and `suspended_at`, clears the completed manual work item and retains the remaining metadata. It must not mark this billing action as a staff/security suspension.

Partial settlement keeps the invoice open and the service suspended. Full verified settlement advances a monthly service from its existing due date by one month while preserving `status=suspended` and `provision_status=done`. The existing `services:lifecycle` job restores access after the invoice is paid; provisioning must not create another resource or reset a password. Repeated settlement is idempotent. Staff/security suspension remains outside automatic billing restoration.

One runtime driver change fixes two gaps. First, a version-1 existing-storage binding can restore its original four access flags, including an enabled SMB setting that differs from the ordinary global default. The override requires matching service, customer, server and box identifiers, the storage driver/server type and the exact safe username/hostname pair. All four snapshot values must be booleans with no extra keys. Invalid or unrelated bindings retain the existing configured access policy; global settings are unchanged.

Second, access updates are asynchronous. The driver reads the exact box before writing and succeeds without another POST if the desired flags are already present. Otherwise it sends one update and confirms only from a bounded fresh readback. Unknown or malformed initial readback causes no write. If an update has not applied yet, the existing retry interval remains in force; a later attempt observes completion before deciding to send again. This confirms provider configuration, not end-user network connectivity.

The isolated regression starts with a delivered, passively bound synthetic account and its earlier pending billing work. It exercises the actual admin suspend/ack endpoints, partial and full confirmed settlement, duplicate settlement, provisioning exclusion and the lifecycle command. A delayed running update must keep local suspension until a later GET confirms all four flags without a duplicate POST. Native driver cases cover invalid/cross-scope snapshot fallback and wrong-resource readback, alongside the existing Storage Box suite.

Runtime deployment scope is only `HetznerStorageProvisioner.php`. No schema, global config, scheduler, financial record, endpoint or provider resource creation is introduced. Tests use synthetic identities and faked HTTP. Production suspension, driver installation and future real payment/restoration need their own receipts; an isolated test is not evidence that the future customer payment has happened.
