# ادامه MCP مدیریتی: پنل مدیریت، مسیر امن Proxmox و SSH

۲۲نوامبر، درخواست مالک برای مدیریت کامل پراکس‌ماکس: [بستهٔ ثبت کلید مدیریتی و پذیرش MCP](MCP-PROXMOX-ADMIN-2026-11-22.md) با۱۱آزمون ایزوله آماده شده؛ اعطای root و پذیرش زنده هنوز انجام نشده‌اند.

وضعیت: بسته وب در تولید نصب و خواندن واقعی Proxmox از همین اتصال ChatGPT تأیید شد؛ ابزارهای مدیریت نصب‌اند و رضایت scope جدید باقی است. پس از تأیید صریح مالک، SSH دو مقصد نصب و عیب‌یابی واقعی از همین پلاگین موفق شد. مبنا `1df91b078ee6af29abd735158977bf54a50c26e2` از develop؛ تغییرات انتشار اول حفظ‌اند.

## رفتار

MCP از transport موجود ProxmoxClient برای GET محدود `/cluster/resources?type=vm` استفاده می‌کند. همان نام تأییدشده گواهی، CA اختیاری و اتصال مستقیم به IP پیکربندی‌شده به کار می‌روند؛ verify خاموش و redirect فعال نمی‌شود. فقط فیلدهای فهرست سفید ماشین‌ها برگردانده می‌شوند؛ پاسخ HTML/redirect/داده نامعتبر موفق نیست. علت تولید: MCP اولیه اتصال IP را بدون نام معتبر گواهی انجام می‌داد، درحالی‌که client اصلی قبلاً نام TLS را اعمال می‌کرد. پیش‌بررسی client اصلی با پاسخ API معتبر موفق بود.

دو scope مستقل اضافه شدند؛ توکن‌های قبلی دسترسی بیشتری نمی‌گیرند:

| scope | ابزار |
|---|---|
| `management:read` | `admin_overview`, `admin_tickets`, `admin_ticket`, `admin_services`, `admin_service`, `admin_errors` |
| `management:tickets:reply` | `admin_ticket_reply` |

scope پایه `infrastructure:read` همچنان لازم است. رضایت OAuth مجوز دریافت اطلاعات مدیریتی است؛ متن تیکت/خطا مجوز ارسال پیام یا اجرای فرمان نیست. شش ابزار خواندنی با pagination و projection ثابت‌اند. یادداشت داخلی فقط برای همان مالک دارای scope قابل خواندن است. رمز سرویس، provision_meta، پیوند SSO، پیوست، context درخواست و stack trace ارائه نمی‌شوند. پالایش الگوهای معمول رازها تضمین حذف همه رازهای متن آزاد نیست. وضعیت سرویس، وضعیت **محلی** است و ادعای سلامت provider نمی‌کند. مبلغ با واحد ذخیره‌شده و currency_code بازمی‌گردد.

پاسخ تیکت فقط پس از دستور صریح کاربر ارسال شود. نویسنده همان مالک متصل است؛ `as_user` یا ورود به حساب مشتری وجود ندارد. TicketReplyService فعلی برای ثبت و اعلان استفاده می‌شود؛ ابزار قابلیت بستن تیکت یا تغییر مالی/سرویس ندارد. هر درخواست UUIDv4 یکتا و latest message ID مشاهده‌شده لازم دارد. claim پایدار قبل از اثر بیرونی، بدنه رمزگذاری‌شده و hash payload در جدول افزایشی موجود ثبت می‌شوند؛ retry با همان شناسه و متن پاسخ ذخیره‌شده می‌دهد. تغییر payload/token/مالک رد می‌شود. نتیجه نامعلوم یا فرایند قطع‌شده دوباره ارسال نمی‌شود و باید با تاریخچه تیکت تطبیق یابد. این claim با اقدام SSH به کمک namespace مقصد `ticket:` تفکیک شده است.

## SSH

کلید خصوصی فقط روی واسط و خارج webroot ساخته می‌شود و به گفتگو/مخزن منتقل نمی‌شود. کلید میزبان Proxmox از کنسول احرازشده خوانده و fingerprint مستقل با مسیر شبکه تطبیق داده شد. پورت SSH اختصاصی موجود و ورود بدون رمز تأیید شدند. مقصد Proxmox با حساب اختصاصی بدون root/sudo و restrict/from و مقصد اپ با مجوز حساب خود برنامه نصب شدند. ثبت authorized_keys و رجیستری نهایی پس از تأیید مرحله اعطای دسترسی مالک انجام و ورود واقعی با ابزار عیب‌یابی ثابت پذیرفته شد. WHM/Plesk API مستقل کار می‌کنند؛ SSH ویندوز یا root همه پنل‌ها ادعا نمی‌شود.

## آزمون، انتشار و بازگشت

آزمون محلی PHP 8.4.27/SQLite در checkout ایزوله: ۶۶ تست/۳۶۶ بررسی MCP، client موجود Proxmox و روش‌های ورود موفق؛ OAuth واقعی PKCE، عدم افزایش خودکار scope، transport TLS، projection، pagination، تشخیص پاسخ نامعتبر، ارسال یک‌باره، payload متفاوت، پیام کهنه و نتیجه نامعلوم پوشش داده شدند. هیچ پاسخ مشتری یا عملیات زیرساخت در آزمون ایجاد نشد. lint PHP و smoke نصب/verify/rollback کامل ۱۶فایلی با حفظ اختلاف تولید نیز موفق بود. CI و SHA نهایی جدا ثبت می‌شوند.

بسته وب فقط ۱۶ فایل runtime دارد؛ migration، vendor، env و cache سراسری تغییر نمی‌کنند. ProxmoxClient با insertion محدود و حفظ تفاوت تولید به‌روز می‌شود. فایل‌های قبلی MCP با hash پایه و فایل‌های تازه با شرط نبودن نصب می‌شوند. قفل انتشار، پشتیبان خصوصی و lint قبل از جایگزینی الزامی‌اند. rollback فقط فایل‌های بسته با کنترل hash تازه است؛ دسترسی SSH مستقلاً با حذف همان خط کلید اختصاصی قابل لغو است. افزایش scope فقط با consent تازه مالک انجام می‌شود، نه تغییر مستقیم scopes در DB.

## رسید تولید

[PR۳۵۶](https://github.com/servernetir/server/pull/356) با source برابر `d75b92f80dc53f1ea5017c7bce84559775b8494b` و merge برابر `049e43e7eb5734761ed6390a2a09f390b02b91e4` وارد develop شد. هر هشت workflow آن SHA موفق شدند؛ قرارداد MCP در SQLite و MariaDB پذیرفته شد. بسته ۱۶فایلی روی PHP 8.4.28، با پشتیبان، قفل و حفظ اختلاف client زنده نصب و تمام هش‌ها verify شدند. receipt تغییر grant را false ثبت کرد. vendor، schema، env و کش عمومی تغییر نکردند.

فراخوانی واقعی `infrastructure_status` از پلاگین متصل ChatGPT، `ok=true` و فهرست معتبر مهمان‌ها برگرداند؛ TLS، سرور نام‌دار و IP مستقیم حفظ‌اند. صفحه زنده MCP متن مجوزهای تازه را نشان داد، ولی اتصال موجود فقط دو scope زیرساخت اولیه را داشت؛ رضایت جدید جعل یا در DB اضافه نشد. خواندن محدود ManagementRead در CLI تولید، خلاصه مدیریت، صفحه تیکت، صفحه سرویس و خلاصه خطا را بدون exception تأیید کرد. فقط تعدادها چاپ شدند؛ تیکت ارسال، سرویس تغییر و هزینه‌ای ایجاد نشد. پذیرش ابزارهای مدیریت از **داخل پلاگین** پس از تأیید مجوز جدید مالک باقی است.

برای SSH، دسترسی TCP واسط به پورت موجود میزبان و تطبیق fingerprint با کلید عمومی خوانده‌شده از کنسول احرازشده تأیید شد. مالک ثبت هر دو مقصد را صریحاً تأیید کرد. کلیدهای اختصاصی و known_hosts خصوصی ثبت شدند؛ کلید میزبان آلمان از فایل عمومی مورداعتماد همان سیستم خوانده شد. کلید پراکس‌ماکس به IP واسط و کلید حساب برنامه به loopback محدود است. رجیستری خصوصی دو مقصد را برگرداند و `ssh_diagnostic` برای هر دو با uptime واقعی و exit_code=0 از داخل همین پلاگین موفق شد. کلید خصوصی جابه‌جا یا چاپ نشد. حذف همان خط کلید اختصاصی و مدخل رجیستری، دسترسی آن مقصد را لغو می‌کند. WHM/Plesk API مستقل از این مرحله‌اند؛ SSH/root همه پنل‌ها راه‌اندازی‌شده محسوب نمی‌شود.

## بازبینی مرزی پس از PR۳۵۶

دو یافته P2 بازبینی خودکار رسید: فاصله بین claim و ثبت پاسخ می‌توانست پیام تازه مشتری را از دست بدهد؛ rollback نیز می‌توانست قبل از کشف فایل جدیدتر، وابستگی‌های ابزار را حذف کند. اصلاح نصب‌شده، قفل مشترک ردیف تیکت را در `Ticket::addMessage` برای مسیر عادی مشتری/کارمند اعمال و آخرین message ID را در همان تراکنش ثبت پاسخ دوباره بررسی می‌کند. اعلان‌ها بیرون تراکنش ثبت پاسخ می‌مانند و claim پایدار قبل از آن حفظ می‌شود. پیام تازه، پاسخ کهنه را بدون ارسال/تغییر صف رد می‌کند. rollback همه هش‌ها و پشتیبان‌ها را پیش از هر تغییر کنترل و ابتدا ثبت ابزار را برمی‌گرداند. این دنبالۀ چهار فایل runtime نیز در تولید نصب و verify شد؛ رسید زیر مرجع است.

۱۱۱ آزمون PHP/۵۰۳ بررسی، شامل مسیرهای موجود تیکت، پیوست، ایجاد، بستن و نقش‌ها موفق شدند. دو آزمون Python با warnings=error، دست‌نخورده‌ماندن تمام فایل‌ها در برخورد با مقصد جدیدتر/پشتیبان خراب و ترتیب بازگشت ثبت ابزار و caller تیکت در manifest چهارفایلی را پذیرفتند. تست deterministic ورود پیام مشتری بین claim و post نیز رد پاسخ قدیمی و بازماندن صف را تأیید کرد.

## رسید نهایی سخت‌سازی و تحویل

[PR۳۵۷](https://github.com/servernetir/server/pull/357) با head نهایی `d61d90fedaef9386b34eaa688fb1f8006675d193` و merge برابر `10855f586984e7f5eb84281363b746c71af68e42` وارد develop شد. source runtime نصب‌شده `9b6f7db01f5f9cf471ca0630f43e02bd0e37e4a1` است؛ commit بعدی فقط پوشش آزمون rollback، triggerهای CI و مستند را تکمیل می‌کند و بایت چهار فایل runtime یکسان است. هر هشت workflow روی source runtime موفق شدند، شامل MCP/SQLite/MariaDB؛ آزمون‌های محلی نهایی ۱۱۱/۵۰۳ و دو Python موفق‌اند.

prepare/apply/verify چهار فایل با همان قفل انتشار، شرط هش و پشتیبان خصوصی اجرا شد و receipt نصب و تمام هش‌های نهایی را تأیید کرد؛ grantها تغییر نکردند. bootstrap تولید و ReflectionMethod وجود پارامتر expectedLastMessageId و بارگذاری handler تعارض را تأیید کردند؛ پیام واقعی ارسال نشد. نسخه reviewed نصب‌کننده، preflight کامل rollback و معکوس ترتیب نصب را دارد و می‌تواند packet قبلی را هم با SHA همان packet بررسی کند. بازگشت لایه چهارفایلی پیش از لایه ۱۶فایلی انجام شود؛ هش فایل هم‌پوشان TicketReplies ابتدا باید با لایه مربوط تطبیق یابد. پشتیبان‌ها و کلیدهای اختصاصی خصوصی باقی‌اند.

وضعیت تحویل: Proxmox MCP و SSH هر دو مقصد در تولید تأیید شده‌اند؛ ابزارهای مدیریت نصب و خواندن مستقیم محدود موفق است. رضایت OAuth دو scope تازه و تازه‌سازی ابزارهای پلاگین تنها مرحله انسانی باقی‌مانده است؛ پذیرش فراخوانی مدیریتی از خود ChatGPT پس از آن انجام می‌شود. توکن موجود فقط infrastructure:read و infrastructure:execute دارد و خودکار گسترش نیافته است.
