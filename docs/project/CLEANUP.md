# پاک‌سازی ایمن مخزن و فایل‌های توسعه

وضعیت این مرحله: **فهرست‌سازی و طرح تصمیم؛ هیچ حذف یا جابه‌جایی انجام نشده است.** خواستهٔ مالک این است که پس از شناخت پروژه، فایل‌های اضافی توسعه تمیز شوند. مقایسهٔ واقعی با cPanel هنوز در این بازنگری انجام نشده است.

## ۱. دو مسئلهٔ متفاوت

پاک‌بودن بستهٔ انتشار با کوچک‌کردن مخزن یکی نیست. مخزن باید تست، دانش، ابزار build و کد زیرساخت را نگه دارد؛ وب‌سرور نباید همهٔ آن‌ها را دریافت کند. همچنین سرور فایل‌های معتبری مثل `.env`، upload، log و state دارد که نباید وارد Git شوند.

معیار حذف این نیست که «روی cPanel نیست»، «نامش قدیمی است» یا «از جست‌وجوی رشته چیزی پیدا نشد». فایل ممکن است از CI، n8n، Worker، Ansible، اسکریپت محلی یا مرحلهٔ rollback مصرف شود؛ ارجاع پویا نیز ممکن است از جست‌وجوی ساده پنهان بماند.

## ۲. طبقه‌بندی اولیه بر اساس snapshot

| گروه | نمونهٔ واقعی | تصمیم این مرحله |
|---|---|---|
| اپ فعال | `website/app/`، `routes/`، `config/`، `lang/`، `resources/`، فایل عمومی لازم | حفظ؛ در بستهٔ وب فقط فهرست مصوب |
| توسعه و آزمون | `website/tests/`، phpunit.xml، composer/package manifest، Vite، ابزارها | حفظ در Git؛ نبودن در تولید طبیعی است |
| زیرساخت مستقل | `infra/ansible/`، `relay/n8n/`، `relay/cloudflare/gpu-proxy.js`، `scripts/arvan-console-worker/` | حفظ؛ مقصد و نسخهٔ نصب‌شده جدا بررسی شوند |
| اپ قدیمی | `app/` ریشه + Dockerfile + docker-compose.yml | کاندید بایگانی یک مجموعهٔ وابسته، نه حذف فوری |
| گزارش توسعه | `website/check_out.txt` | محتوای خروجی تشخیصی دارد؛ کاندید حذف بعد از بررسی ارجاع و نیاز نگهداری |
| lock نامرتبط/ناقص | `package-lock.json` ریشه با `packages: {}` | کاندید حذف/تعیین تکلیف؛ جای lock اپ را نمی‌گیرد |
| انتشارهای موردی | `scripts/deploy-*.sh` و ابزارهای تاریخی | برای هر اسکریپت مصرف، آخرین انتشار و rollback بررسی شود |
| دانش و شواهد | گزارش‌های تاریخ‌دار ریشه، NETWORK-CURRENT و CLAUDE | حفظ؛ دسته‌بندی/انتقال بعدی فقط با اصلاح لینک و وابستگی‌ها |
| وضعیت و راز محیط | `.env`، storage زنده، backup/dump، توکن و اعتبارنامه | نه آپلود در Git؛ نه حذف از سرور در این مرحله |

`.m3-verify-setup.sh`، ابزارهای `tools/`، منابع `seo/` و تنظیمات `.claude/` نیز باید مالک و مصرف‌کنندهٔ مشخص داشته باشند؛ از نام یا نبودن روی وب‌سرور نتیجهٔ بلااستفاده‌بودن نگیرید. مسیرهای قدیمیِ فقط نام‌برده‌شده در docs، مثل launch/update محلی، باید ابتدا وجودشان در SHA جاری سنجیده شود.

## ۳. inventory مورد نیاز

سه فهرست مستقل تهیه شود: فایل‌های tracked در SHA مشخص develop؛ فایل‌های مقصد cPanel با نگاشت صحیح؛ و اجزای مستقر بیرون از cPanel. فایل‌های محیط/مشتری از محتواسنجی و خروجی عمومی حذف شوند. برای آن‌ها فقط وجود/نوع و مالکیت در فهرست خصوصی ثبت شود.

روی checkout محلی سالم، دستورهای زیر صرفاً برای بررسی‌اند و چیزی حذف نمی‌کنند:

```bash
git status --short
git branch --show-current
git rev-parse HEAD
git ls-tree -r --name-only HEAD
git ls-files --error-unmatch website/check_out.txt
# نامزدهای مشخص؛ نبود نتیجه اثبات بی‌استفاده‌بودن نیست
git grep -n -F 'check_out.txt' HEAD -- .
git log -5 -- website/check_out.txt
```

پس از این بازنگری، خود این سند هم در جست‌وجوی نام فایل پیدا می‌شود؛ ارجاع مستند را از وابستگی اجرایی جدا کنید. برای فایل ساخته‌شده، generated header، build script و مصرف‌کنندهٔ واقعی نیز بررسی شوند. ابزار inventory نباید `--delete`، migration، تغییر permission، تماس provider یا خواندن راز داشته باشد.

### قرارداد فهرست هر نامزد

```text
path / component / tracked-at-SHA / file-type
classification: runtime | development | external-runtime | historical | generated | sensitive-state | unknown
size / content-hash (فقط فایل کد غیرمحرمانه)
references: runtime / tests / build / docs / deploy / rollback / external-consumer
production mapping / remote presence / evidence time
owner / reason / proposed action / backup / restore path
decision: KEEP | EXCLUDE-FROM-DEPLOY | ARCHIVE-CANDIDATE | DELETE-CANDIDATE | INVESTIGATE
approval / verification result
```

فهرست خصوصی سرور نباید محتوی `.env`، دادهٔ مشتری یا لاگ خام را به یک PR عمومی منتقل کند. اسکن فعلی شامل بررسی کامل تاریخچه برای secrets نیست؛ نبود کشف، گواه نبود راز نیست.

## ۴. روش درست مقایسه با cPanel

ابتدا همان نگاشت [DEPLOYMENT](DEPLOYMENT.md) اعمال شود: `website/public/` به `public_html/` و فایل اجرایی اپ به `servernet_app/`. `index.php` مخصوص تولید، storage/state، فایل‌های میزبان و خروجی build استثناهای صریح‌اند.

پس از تطبیق، خروجی در چهار دسته باشد:

- **فقط Git و مورد انتظار:** تست، docs، ابزار build و کد جزء بیرونی؛ اقدام حذف ندارد.
- **فقط سرور و مورد انتظار:** فایل محیط، state، upload، log، dependency/artifact مصوب یا adapter سرور؛ نیاز به حفظ و مستندکردن دارد.
- **کد متناظر با محتوای متفاوت:** احتمال hotfix یا deploy ناقص؛ قبل از هر نوشتن reconciliation لازم است.
- **نامعلوم:** مقصد/مصرف‌کننده روشن نیست؛ قرنطینه یا حذف خودکار مجاز نیست.

«فقط سرور» با «فقط Git» را به‌صورت کور برای همسان‌سازی حذف نکنید. مقایسهٔ hash فقط روی فایل‌های متناظر و با یک الگوریتم انجام شود؛ Git blob SHA با SHA-256 بایت‌ها متفاوت است.

## ۵. ترتیب عملی پاک‌سازی بعدی

**مرحله A — بستهٔ انتشار را محدود کنید.** با allowlist/manifest جلو ورود ابزارها و گزارش‌ها به public را بگیرید. این مرحله از حذف سورس مفیدتر و کم‌ریسک‌تر است؛ پیکربندی خودکار انتشار فعلی هنوز باید شناسایی شود.

**مرحله B — نامزدهای کوچک.** نخست فایل تشخیصی `website/check_out.txt` و lock خالیِ ریشه را با جست‌وجوی وابستگی و build بررسی کنید. حذف فقط در تغییر مستقل با آزمون و diff مشخص انجام شود. نبود lock اپ باید جدا حل شود، نه با انتقال lock خالی.

**مرحله C — مجموعهٔ legacy.** ریشهٔ `app/`، Dockerfile و compose به‌صورت یک مجموعه بررسی شوند. مصرف در ابزارهای توسعه، deployment و مستندات باید روشن شود. گزینهٔ بایگانی در tag یا محل مصوب، سپس حذف از working tree، با تأیید مالک تعیین شود؛ هیچ تصمیمی در این بازنگری اجرا نشده است.

**مرحله D — اسکریپت‌های موردی و گزارش‌ها.** ابزار جاری از اسکریپت یک‌بارمصرف جدا شود؛ اسکریپت موردی نباید صرفاً به‌علت وجود در پوشهٔ scripts دوباره اجرا شود. هنگام انتقال گزارش‌ها همهٔ لینک‌ها و ابزارهای خوانندهٔ مسیر ثابت اصلاح شوند. ترتیب rollback یا شواهد پذیرش حذف نشود.

**مرحله E — سرور.** فقط پس از inventory مجاز و خواندنی، محدودهٔ دقیق پاک‌سازی cPanel تعیین شود. backup خصوصی و مسیر بازیابی پیش از هر تغییر لازم‌اند. نبودن نسخهٔ سورس در Git هیچ مجوزی برای حذف فایل زنده نمی‌دهد.

## ۶. شرط پذیرش

تغییر پاک‌سازی باید کوچک و جدا از تغییر عملکردی باشد؛ تعداد و مسیر فایل‌ها، علت، ارجاع‌های بررسی‌شده، پشتیبان، نتیجهٔ آزمون و بازگشت ثبت شوند. رفتار app، سه زبان، build و تست مرتبط نباید تغییر ناخواسته کنند. برای انتقال، ارجاع‌های scripts/CI/docs و جزء بیرونی نیز بررسی شوند.

حذف فایل از آخرین commit راز را از تاریخچهٔ Git پاک نمی‌کند. در کشف معتبر راز، گردش/ابطال اعتبارنامه و رسیدگی به تاریخچه عملیات امنیتی جدا هستند. هیچ رمز یا دادهٔ نمونهٔ مشتری در گزارش عمومی بازنشر نشود.
