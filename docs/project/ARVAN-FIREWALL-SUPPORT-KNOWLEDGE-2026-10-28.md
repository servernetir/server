# سیاست فایروال آروان و دانش پاسخ‌گویی پشتیبانی

۲۸ اکتبر ۲۰۲۶. گزارش توسعه‌دهندگان و دانش داخلی؛ فاقد اطلاعات مشتری، IP سرور مشتری، متن خصوصی تیکت و شناسهٔ قواعد عملیاتی.

## وضعیت تأییدشده

با درخواست صریح مالک، گروه `servernet` در شش ناحیهٔ فعلی حساب، همهٔ پورت‌های TCP/UDP و ICMP را برای ورودی و خروجی IPv4/IPv6 مجاز می‌کند. چهار گروه گسترش یافتند، دو گروه ساخته شدند و دو اتصال با حفظ گروه‌های قبلی افزوده شد؛ جمع تغییر ۲۴ قانون بود. قواعد قبلی، SSH و وضعیت توان مهمان‌ها حفظ شدند.

ناحیه‌ها: `ir-southwest1-a`، `ir-thr-ba1`، `ir-thr-si1`، `ir-thr-fr1`، `ir-tbz-sh1` و `eu-west1-a`. در snapshot زندهٔ ۱۳:۳۳ تهران، پنج سرور موجود و انتخاب گروه برای سفارش جدید در هر شش ناحیه تطبیق شدند. این وضعیت تاریخ‌دار است؛ سرویس یا ناحیهٔ بعدی دوباره بررسی شود.

تنظیم پایدار `arvan_security_group=servernet` است. متد واقعی انتخاب گروه، شناسهٔ گروه باز همان ناحیه را برمی‌گرداند؛ برای آزمون مسیر انتخاب، ماشین جدید ساخته نشد.

**استثنای SMTP:** پنل آروان محدودیت مستقل پیش‌فرض خروجی روی ۲۵ و ۴۶۵ را اعلام می‌کند. بازکردن قواعد حساب، رفع آن را ثابت نمی‌کند. هیچ تیکت تأمین‌کننده یا پیام آزمایشی در این کار ارسال نشد.

## قرارداد API و تفسیر

API قدیمی `/ecc/v1/regions/{region}/securities` هنگام این تغییر، قواعد تازهٔ پنل را ناقص نشان می‌داد. مرجع فعلی:

- گروه‌ها: `GET /ecc/v2/firewall/{region}/list`
- قواعد گروه دقیق: `GET /ecc/v2/firewall/{region}/details/{groupId}`
- ساخت قانون، فقط در عملیات مجاز جدا: `POST /ecc/v2/firewall/{region}/rules/{groupId}/create` با `direction`, `ether_type`, `protocol`, `port_min`, `port_max`, `remote_ip`.

`securityGroupIds` ابتدا v2 را می‌خواند؛ fallback قدیمی و رد نام دستی حل‌نشده حفظ‌اند. cache به `arvan.sg-id.v4` رفت تا انتخاب قبلی برای گروه تازه باقی نماند. `inspectFirewall` فقط هویت ماشین و گروه متصل را می‌پذیرد و قواعد را محدود و اعتبارسنجی می‌کند؛ بدنهٔ خام سرور و اعتبارنامه به مدل نمی‌رسند. خطا، گروه نامرتبط، داده ناقص و عبور از سقف قواعد، unavailable هستند.

پذیرش واقعی مدل اشکال دیگری را پیدا کرد: `protocol=""` و پورت صفر/صفر در این API، در پنل «TCP,UDP / همه پورت‌ها» است، اما مدل آن را نبود UDP می‌دانست. خروجی اکنون `protocol_display`, `port_scope`, `address_scope` و `all_tcp_udp_ports` دارد. CIDR محدود و TCP بدون UDP، مجوز سراسری هر دو پروتکل نمی‌شوند.

writer روشن می‌کند `repairs_performed=false` به همین بررسی خواندنی مربوط است؛ از آن نمی‌توان نبود تغییر قبلی اپراتور را نتیجه گرفت. قواعد زنده می‌توانند گزارش قدیمی کارکنان را جایگزین کنند. برای پورت مجاز، پیشنهاد بازکردن مجدد داده نشود.

## روال پاسخ به تیکت

۱. مالکیت از رابطهٔ سرویس و ماشین همان مشتری احراز شود. فهرست خالی WHM/Plesk نبود VPS را ثابت نمی‌کند؛ سرویس ابری می‌تواند `server_id` نداشته باشد. اطلاعات موجود دوباره خواسته نشوند؛ چند سرویس یا inventory ناقص انتخاب قطعی نمی‌دهند.

۲. گروه متصل و قواعد تازهٔ همان سرویس ملاک‌اند؛ گروه Default نامرتبط، سیاست تاریخی یا متن پشتیبانی قبلی کافی نیست. نام واقعی زیرساخت و جزئیات خصوصی/تأیید داخلی وارد پاسخ مشتری نشوند.

۳. قاعدهٔ باز، سلامت listener، فایروال مهمان و دریافت واقعی UDP نیست. TCP refused با timeout و اتصال موفق متفاوت است و علت دقیق را تعیین نمی‌کند. ارسال UDP بدون دریافت هماهنگ، اثبات تحویل نیست.

۴. پاسخ کوتاه و هم‌زبان مشتری باشد؛ پورت‌های تازه در پیگیری جای بازهٔ قبلی را نگیرند. درخواست صریح مشتری رضایت خودش است؛ آن را دوباره نخواهید. این رضایت، مجوز خودکار عامل برای تغییر یا ارسال نیست.

نمونه، فقط پس از تأیید جاری قواعد:

> سلام. بررسی فعلی نشان می‌دهد پورت‌های درخواستی در فایروال زیرساخت مجاز هستند. لطفاً اتصال را دوباره آزمایش کنید؛ اگر مشکل باقی بود، زمان و نتیجهٔ آزمون را بفرستید تا سرویس داخل سرور و ادامهٔ مسیر بررسی شود.

متن آماده، پاسخ ارسال‌شده و اتصال رفع‌شده سه وضعیت متفاوت‌اند؛ پاسخ عمومی تازه‌ای در این کار ارسال نشد.

## دانش پایدار هرمس

شش مرجع تاریخ‌دار از بستهٔ `infra/hermes/support-firewall-20261028/knowledge-documents.json` در کتابخانهٔ owner-scoped ثبت و بازخوانی شدند؛ تعداد منابع از ۹۹ به ۱۰۵ رسید. همه reference-only، فاقد ادعای سلامت جاری و خصوصی مالک‌اند. ۱۷ قاعدهٔ پیشین حفظ شدند و برای جا دادن اطلاعات تازه از سقف متن بیرون رانده نشدند.

موضوع‌ها: سیاست باز/SMTP، API v2، مالکیت VPS، شواهد شبکه، پاسخ کوتاه/پیگیری و ماندگاری/rollback. مسیر پاسخ تیکت نیز playbook ثابت شبکه می‌گیرد؛ سیاست آروان فقط برای سرویس تأییدشدهٔ همان زیرساخت اضافه می‌شود. چک قدیمی یا متعلق به سرویس دیگر معتبر نیست. دانش، مجوز اجرایی جدید نمی‌سازد.

کل runtime قدیمی پشتیبانی Hermes در این پایهٔ develop نسخه‌بندی نشده بود. snapshotهای اصلاح‌شده در `infra/hermes/support-firewall-20261028/` خارج از autoload اپ ثبت می‌شوند؛ bootstrap یا مسیر HTTP دوم نمی‌سازند. مقصد تولید و کنترل اختلاف در README همان پوشه آمده است.

## آزمون و پذیرش

پایهٔ بررسی `755cb72e7d3bd8f951a0f0513e7c796da627e83d`؛ PHP بومی ۸.۴.۲۶، checkout ایزوله و Composer lock یکسان؛ بدون `.env`، داده یا اعتبارنامهٔ تولید و با HTTP جعلی.

- مجموعهٔ قدیمی آروان روی فایل دقیق پایه و تغییر، هر دو ۵۷ تست / ۹۹ assertion: ۳۲ موفق، ۱۱ failure و ۱۴ error. نوع و شناسهٔ هر ۲۵ مورد یکسان بود؛ از جمله fixture جدول `arvan_create_attempts` و نرخ ارز. اصلاح مالی یا migration جانبی انجام نشد.
- اجرای ترکیبی نهایی ۸۰ تست / ۱۶۰ assertion: ۵۵ موفق و همان ۲۵ مورد پایه. suite کامل سبز اعلام نمی‌شود؛ خلاصهٔ فاقد داده خصوصی در `validation.json` ثبت است.
- پذیرش native نهایی، بازبودن هر چهار ترکیب جهت/خانواده و پاسخ صحیح دربارهٔ پورت‌های درخواستی را نشان داد؛ تحلیل ۷۵۴ و پاسخ ۵۳۴ نویسه بود. این نمونه تضمین بی‌خطابودن تمام جواب‌های آینده نیست.

## نصب، دامنه و بازگشت

فایروال حساب قبلاً با اجازهٔ مالک تغییر و بازخوانی شد. در آموزش، playbook، writer و خروجی خواندنی درایور با پشتیبان، کنترل هش، lint، جایگزینی اتمی و ابطال OPcache همان مسیرها نصب شدند. شبکه، VM lifecycle، کیف/صورتحساب، cron و منابع state عامل‌های country-routing/port-forward تغییر تازه‌ای برای ثبت دانش نداشتند.

رسید و پشتیبان خصوصی زیر `storage/app/private/arvan-open-firewall-20261028` و `storage/app/private/hermes-firewall-knowledge-20261028` باقی می‌مانند؛ وارد Git نمی‌شوند. helperها header تصادفی و انقضای کوتاه داشتند و پیش از اجرا حذف می‌شدند.

بازگشت کد فقط با هش جاری، پشتیبان متناظر، حفظ تغییرهای بعدی و lint/OPcache باشد. برای دانش، فقط شش ID همین بسته با تطبیق hash/revision اصلاح شوند؛ کل state قبلی روی منابع تازه بازنویسی نشود. رسیدها و سابقه تیکت حفظ شوند. rollback شبکه مستقل و نیازمند اجازهٔ مالک است: فقط شناسه‌های افزودهٔ رسید خصوصی، با حفظ SSH، قواعد قبلی و اتصال‌های بعدی بررسی شوند. helperها کورکورانه تکرار نشوند.

مرجع عمومی: [راهنمای رسمی فایروال آروان](https://docs.arvancloud.ir/fa/cloud-server/firewall/). وضعیت هر سرور از API جاری همان سرویس می‌آید.
