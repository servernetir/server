## 18 October: pre-release multi-tab defect found; fix prepared, public gate still OFF

The acceptance review found a deterministic shared-cookie race in the deployed Worker: launch A sets cookie A; launch B overwrites it with B; if socket A opens afterwards, it can consume B's one-use claim and display the wrong VM belonging to the same owner. No cross-customer bypass was demonstrated, but wrong-VM control is sufficient to block broad rollout. The earlier action-time question about public access is not evidence that this defect was accepted or that activation occurred.

Prepared a Worker-only fail-closed fix in `scripts/arvan-console-worker/worker.mjs`. Launch returns only a domain-separated SHA-256 fingerprint of its random HttpOnly session. Both clients supply this per-tab binding on the socket request. The Worker requires the binding to match the current cookie before broker claim or provider contact; overwrite causes409 without consuming a different grant. The fingerprint alone cannot authorize a socket and the actual session/provider credentials remain out of URLs. Only the single validated binding query is allowed. All30 Worker/client tests pass, including a deterministic two-tab overwrite regression and malformed/missing/fingerprint-only rejection. Broker17 tests/40 assertions also passed before this Worker-only change.

This patch is LOCAL, not yet deployed. Preserve existing Worker bindings/routes and both console gates; deploy only servernet-vnc, then repeat real private501 image/input/reconnect before public enablement. Older already-loaded clients fail closed and need a fresh console launch. This is safe rejection of a racing tab, not a promise that simultaneous launches both succeed. No DNS or portal Worker changes are needed. The owner separately requested permanent deletion of501; final deletion confirmation is pending. If deletion occurs first, do not silently use another customer's machine or create a replacement for acceptance.
