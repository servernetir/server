## چهار اصلی که کل سیستم روی آن ایستاده

### ۱. پول هرگز اعشاری نیست

همه‌ی مبالغ `BIGINT` در **واحد فرعی** ذخیره می‌شوند و نمای هر ارز یک بار در
جدول `currencies` تعریف می‌شود:

```
IRT  exponent 0   →  490000  یعنی ۴۹۰٬۰۰۰ تومان
EUR  exponent 2   →  1290    یعنی €12.90
```

**تومان، نه ریال.** WHMCS ریال برمی‌گرداند و اشتباه ضربدر ۱۰ یک بار در این
پروژه اتفاق افتاده است.

### ۲. قیمتی که نشان می‌دهیم، قیمتی است که می‌توانیم پایش بایستیم

هیچ قیمتی به مشتری نمایش داده نمی‌شود مگر از یک ردیف `price_quotes` با پنجره‌ی
`honour_until` آمده باشد. اگر رسیلری نتواند تحویل دهد، به‌جای قیمت،
`orderable=false` با دلیل برمی‌گردد.

این همان قاعده‌ای است که مشکل «۲۰ دلار → ۲ دلار → not free» را از ریشه می‌بندد.

### ۳. تحویل باید idempotent باشد

هر کار تحویل یک ردیف `provisioning_tasks` است با کلید یکتا. اگر صف کار را
دوباره اجرا کند، **سرور دوم ساخته نمی‌شود**. این تنها چیزی است که بین شما و
فاجعه‌ی «۵۰ سرور تکراری در یک شب» ایستاده.

### ۴. دو نصب مستقل، بدون replication

```
servernet.ir     →  سرور ایران   →  پیش‌فرض fa  →  تومان  →  درگاه ایرانی
servernet.cloud  →  سرور آلمان   →  پیش‌فرض en  →  یورو   →  کارت + کریپتو
```

مشتری در دیتابیس سروری زندگی می‌کند که آنجا پرداخت کرده. مشتری ایرانی که سرور
آلمانی می‌خرد: سفارش و فاکتور و سرویس در دیتابیس ایران، فقط تماس API به خارج
می‌رود.

## جریان اصلی

```
جستجو/انتخاب
    ↓  price_quotes  (قیمت قابل‌احترام، با انقضا)
سبد → سفارش (orders)
    ↓
فاکتور (invoices)          ← سند حقوقی، شماره‌ی پیوسته و بدون شکاف
    ↓
پرداخت (payments)          ← درگاه ایرانی | کریپتو | کیف پول
    ↓  فقط بعد از تأیید پرداخت
provisioning_tasks         ← idempotent، با retry و checkpoint
    ↓
services                   ← اشتراک با تاریخ تمدید و وضعیت
    ↓  چرخه‌ی خودکار
فاکتور تمدید → یادآوری → تعلیق → خاتمه
```

## ماژول‌ها

```
app/
  Modules/
    Identity/       مشتری، پروفایل، مدارک، ورود
    Catalog/        محصول، گزینه، قیمت، موجودی
    Order/          سبد، سفارش
    Billing/        فاکتور، پرداخت، کیف پول، تمدید
    Provisioning/   درایورها، نودها، وظایف
    Domain/         رسیلری‌ها، جستجو، ثبت، تمدید
    Support/        تیکت، اعلان
    Ops/            کران، گزارش، لاگ، نقش‌ها
```

هر ماژول یک **قرارداد (interface)** دارد تا افزودن ارائه‌دهنده‌ی جدید یک کلاس
باشد، نه تغییر در ده جا:

| قرارداد | برای |
|---|---|
| `ProvisioningModule` | WHM، Plesk، DirectAdmin، Proxmox، Hetzner، OVH… |
| `DomainRegistrar` | OpenProvider، CentralNic، IRNIC… |
| `PaymentGateway` | درگاه ایرانی، کریپتو، کیف پول |
| `ProfileType` | حقیقی، حقوقی |
| `SocialProvider` | گوگل، اپل |
| `ScheduledTask` | هر کار زمان‌بندی‌شده |
| `NotificationEvent` | هر رویدادی که اطلاع‌رسانی دارد |

## تصمیم‌هایی که باید قبل از اولین خط کد گرفته شوند

### ۱. دیتابیس: SQLite دیگر کافی نیست

الان SQLite است، و session و cache و queue هم رویش‌اند. یک سیستم صورت‌حساب یعنی
نوشتن همزمان روی همان فایل. با `busy_timeout` تنظیم‌نشده، نتیجه `database is
locked` است نه صبر کردن.

**پیشنهاد: MariaDB.** این یک انتخاب بازگشت‌ناپذیر است — بعد از اولین فاکتور
واقعی، مهاجرت دردناک می‌شود.

### ۲. ترتیب ساخت

هر مرحله روی مرحله‌ی قبل سوار است:

```
۱) دیتابیس + Identity          ← بدون مشتری هیچ‌چیز معنا ندارد
۲) Catalog                     ← بدون محصول سفارشی نیست
۳) Order + Billing + یک درگاه  ← اولین درآمد واقعی
۴) Provisioning + یک درایور    ← پیشنهاد: WHM (ساده‌ترین)
۵) Domain + یک رسیلری          ← پیشنهاد: OpenProvider
۶) Support + Ops               ← تیکت و گزارش
۷) بقیه‌ی درایورها و رسیلری‌ها  ← حالا فقط کلاس اضافه می‌شود
```

**اولین فاز قابل‌عرضه:** مرحله ۱ تا ۴. یعنی مشتری ثبت‌نام می‌کند، هاست
می‌خرد، پرداخت می‌کند، و اکانتش خودکار ساخته می‌شود. بقیه بعداً.

### ۳. سؤال‌های باز

- **درگاه پرداخت ایرانی:** کدام؟ (زرین‌پال، آیدی‌پی، …)
- **کریپتو:** کدام سرویس؟ چند تأیید برای نهایی‌شدن؟
- **مهاجرت داده:** مشتریان فعلی WHMCS منتقل شوند یا از صفر؟
- **خاموشی WHMCS:** یک‌باره یا موازی؟
- **مالیات:** فاکتور رسمی با مالیات بر ارزش افزوده لازم است؟
