# دو تصمیم: ساختار دیتابیس و سرور فیزیکی

## ۱. دیتابیس — پیشنهاد: **یک MariaDB برای هر نصب، همه‌چیز ادغام‌شده**

### وضعیت فعلی

سایت اصلی روی SQLite است با داده‌ی **بسیار کم**:

| | رکورد |
|---|---|
| پست (بلاگ + پایگاه دانش) | ~۲۵ روی پروداکشن |
| ترجمه‌ها | ~۷۵ |
| نظرات | ۰ |
| کاربران | ۰ (فقط ادمین) |

حجم فایل: ۴۷۲ کیلوبایت.

### پیشنهاد

**بلاگ و پایگاه دانش و نظرات را با سیستم صورت‌حساب در یک دیتابیس MariaDB ادغام کنیم.**
هر نصب (ایران / آلمان) یک MariaDB دارد که **همه‌چیز** در آن است.

```
servernet.ir    →  MariaDB ایران   →  بلاگ + پایگاه دانش + نظرات + مشتری + فاکتور + سرویس
servernet.cloud →  MariaDB آلمان   →  همان ساختار، داده‌ی جدا
```

### چرا ادغام، نه دو دیتابیس جدا

**الف) داده ناچیز است — الان ارزان‌ترین لحظه برای مهاجرت است.**
~۱۰۰ رکورد. بعد از اولین هزار فاکتور واقعی، همین کار دردناک می‌شود.

**ب) یک اپ لاراول = یک اتصال ساده.**
با دو اتصال، `join` بین جدول‌ها ممکن نیست و `transaction` روی هر دو کار نمی‌کند.
یعنی هر جا بخواهید نظر یک مشتری را به حساب کاربری‌اش وصل کنید، باید دستی
در PHP جوین بزنید.

**ج) نظرات به مشتری وصل خواهند شد.**
الان نظر فقط نام و ایمیل دارد. وقتی پنل کاربری راه افتاد، طبیعی است که نظرِ
کاربرِ واردشده به `customers.id` وصل شود — که با دو دیتابیس نشدنی است.

**د) یک پشتیبان، یک بازیابی، یک جای نگاه کردن.**

### آنچه SQLite را رد می‌کند

سیستم صورت‌حساب یعنی نوشتن هم‌زمان: session + cache + سفارش + فاکتور + صف.
SQLite با `busy_timeout` تنظیم‌نشده، به‌جای صبر کردن `database is locked`
می‌دهد. برای سایت محتوایی مشکلی نبود؛ برای فروشگاه هست.

### قدم‌های مهاجرت

۱. ساخت دیتابیس MariaDB روی cPanel (هر نصب یکی)
۲. تغییر `DB_CONNECTION=mysql` و اطلاعات اتصال در `.env` سرور
۳. `migrate` روی دیتابیس خالی
۴. انتقال ~۱۰۰ رکورد پست/ترجمه با یک کامند
۵. تأیید سلامت بلاگ و پایگاه دانش، بعد ادامهٔ ساخت صورت‌حساب

## ۲. سرور فیزیکی (Dedicated) — شکاف طراحی

`dedicated` در انواع محصول هست، ولی **حوزهٔ provisioning فقط تحویل آنی و
API-محور را فرض کرده**. سرور فیزیکی اساساً فرق دارد:

| | VPS / هاست | سرور فیزیکی |
|---|---|---|
| تحویل | ثانیه‌ای، API | ساعت تا روز |
| موجودی | کشسان | **محدود به سخت‌افزار واقعی** |
| مراحل | یک تماس API | تخصیص، نصب، IP، تحویل |
| لغو | آنی | ممکن است هزینهٔ برگشت داشته باشد |

### آنچه باید اضافه شود

**الف) حالت تحویل روی محصول**

```
products.delivery_mode:  instant | queued | manual
```

- `instant` — VPS، هاست: همان لحظه ساخته می‌شود
- `queued` — سرور فیزیکی با API (مثل Hetzner Robot): سفارش ثبت، تحویل با تأخیر
- `manual` — سرور فیزیکی خودمان: کارمند باید کاری انجام دهد

**ب) وضعیت جدید در چرخهٔ سرویس**

```
services.status:  ... | awaiting_provision
```

یعنی «پول گرفته شده، سخت‌افزار در حال آماده‌سازی». بدون این وضعیت، یا باید
سرویس را زودتر از موعد `active` کنیم (دروغ به مشتری) یا `pending` نگهش داریم
(که با «منتظر پرداخت» اشتباه می‌شود).

**ج) موجودی سخت‌افزار واقعی**

جدول `dedicated_inventory`: هر ماشین فیزیکی یک ردیف — مشخصات، دیتاسنتر،
وضعیت (`in_stock` / `reserved` / `deployed` / `maintenance`)، و سرویسی که
رویش نشسته.

**بدون این، دو مشتری می‌توانند آخرین سرور موجود را هم‌زمان بخرند.**

**د) صف کار دستی برای ادمین**

مراحل تحویل دستی باید در پنل مدیریت دیده شوند: «سفارش #۱۴۸۲۳ منتظر تخصیص
سخت‌افزار است». همان `provisioning_tasks` است ولی با `mode=manual` که به‌جای
اجرای خودکار، در صف ادمین می‌نشیند.

**ه) اعلام زمان تقریبی به مشتری**

مشتری که سرور فیزیکی می‌خرد باید بداند «تا ۲۴ ساعت آینده تحویل می‌شود» —
وگرنه ۲۰ دقیقه بعد تیکت می‌زند.

### ریسک که کارفرما احتمالاً دست‌کم گرفته

**فروش چیزی که موجود نیست.** با VPS، اگر ظرفیت تمام شود نود بعدی را می‌سازید.
با سرور فیزیکی، اگر بفروشید و سخت‌افزار نباشد، یا باید پول برگردانید یا
مشتری روزها منتظر بماند. موجودی واقعی باید **قبل از پرداخت** رزرو شود، نه بعد.
