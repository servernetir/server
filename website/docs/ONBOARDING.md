# ورود به پروژهٔ ServerNet

نرخ ارز، ۱۷ اکتبر ۲۰۲۶: سورس انتشار باید اتصال نوسان برای دلار آمریکا شخص، یورو حواله و تتر و `fx:dollar` با `everySixHours()` را حفظ کند. نرخ/زمان/منشأ و برنامهٔ شش‌ساعته با تست‌های `NavasanExchangeRateTest`، `NavasanStoredSourceTest`، `NavasanPricingAdminTest` و `FetchDollarTest` محافظت می‌شوند. تغییر صرفاً نصب‌شده روی سرور کافی نیست؛ پیش از انتشار بعدی، ثبت این تغییر در شاخهٔ انتشار و تطبیق با سورس زنده لازم است. وضعیت نصب و پذیرش در [گزارش بازیابی](../../NAVASAN-FX-RECOVERY-2026-10-17.md) ثبت می‌شود.

بازنگری: ۱۴ اکتبر ۲۰۲۶. مرجع کد بررسی‌شده: `f455d44ed928fd01905da1d64d64a8b887324e60` از `develop`.

ترتیب مطالعه: [نمایهٔ پروژه](../../docs/project/README.md) ← این سند ← بخش مرتبط [CLAUDE.md](../CLAUDE.md) ← کد واقعی. این راهنما اطلاعات منقضیِ نسخهٔ قبلی دربارهٔ README ریشه، دیتابیس تولید و تعداد تست‌ها را جایگزین می‌کند؛ جزئیات تاریخی در Git و CLAUDE باقی‌اند.

## ۱. پنج واقعیت پایه

| موضوع | قرارداد |
|---|---|
| شاخهٔ اصلی کار | `develop`؛ `main` پیش‌فرض GitHub هنگام بررسی بود، نه مرجع کاری مالک |
| ریشهٔ اپ | `website/`؛ اجرای دستورهای Laravel از همین پوشه |
| فناوری اعلام‌شده | PHP `^8.3`، Laravel `^13.8`؛ PHP 8.4 مبنای محیط ثبت‌شده |
| دیتابیس | SQLite پیش‌فرض محلی و تست؛ MariaDB تولید طبق گزارش راهنمای فنی، نه سنجش زندهٔ این بازنگری |
| محیط تولید | cPanel، اپ خارج از webroot؛ انتشار از روی فهرست فایل، نه کپی کامل مخزن |

`infra/`، `relay/` و ابزارهای تست/انتشار بخش‌های معتبر پروژه‌اند، حتی اگر در cPanel نباشند. README ریشه اکنون سند معتبر ورودی است، نه فایل متروک.

## ۲. محیط محلی ایزوله

هیچ کپی `.env`، دیتابیس مشتری یا توکن واقعی به محیط توسعه نیاورید. پیش از نصب، `composer.json` و اسکریپت‌های نصب را بخوانید. دستورهای زیر فقط روی checkout محلیِ جدید هستند:

```bash
git clone --branch develop https://github.com/servernetir/server.git
cd server/website
php -v
composer install
# فقط در محیط جدید؛ فایل محیط موجود را بازنویسی نکنید.
cp -n .env.example .env
php artisan key:generate
# در .env محلی: DB_CONNECTION=sqlite؛ DB_URL خالی؛ بدون راز تولید.
touch database/database.sqlite
php artisan migrate
php artisan serve
```

این نمونه برای shell سازگار با Bash است؛ در ویندوز عملیات فایل را با معادل همان shell انجام دهید. تولید کلید فقط برای محیط جدید است. seederها را پیش از اجرای انتخابی بررسی کنید؛ `--seed` عمومی بخشی از دستور شروع الزامی نیست. `composer setup` شامل migration و build است و برای تولید استفاده نمی‌شود.

اکستنشن‌های اجباری تست طبق `tests/bootstrap.php`: `curl`, `dom`, `fileinfo`, `gd`, `intl`, `mbstring`, `pdo_sqlite`, `sodium`, `zip`. برای محیط سازگار با MariaDB، نیازهای `pdo_mysql` و نسخهٔ واقعی سرور را نیز بررسی کنید. ملاک نهایی، lock وابستگی‌ها و بررسی platform است، نه صرفاً نسخهٔ PHP نوشته‌شده در این سند.

### Frontend

`package.json` دستورهای `npm run dev` و `npm run build` و وابستگی‌های Vite/Tailwind دارد. در snapshot بررسی‌شده **`website/package-lock.json` وجود ندارد**؛ lock ریشه `packages: {}` است و وابستگی‌های اپ را قفل نمی‌کند. `.npmrc` اجرای install script را غیرفعال کرده است؛ بدون بررسی امنیتی آن را حذف نکنید.

برای تغییر frontend، ابتدا مشخص کنید فایل از Vite ساخته می‌شود یا مستقیماً در `public/` مصرف می‌شود. تثبیت نسخهٔ Node و lockfile باید در تغییر جداگانه با نصب تمیز و تست build انجام شود؛ تا آن زمان این راهنما `npm ci` یا build بازتولیدپذیر را انجام‌شده فرض نمی‌کند. `node_modules/` مقصد انتشار نیست.

## ۳. تستی که واقعاً معنی دارد

```bash
# فقط از website/ در checkout تست، نه پوشهٔ تولید
php artisan test
node tests/js/otp-input.test.cjs
node ../relay/n8n/verify-and-map-template.test.js
node ../relay/n8n/evaluate-and-respond.test.js
```

دستورهای بالا نقطهٔ شروع موجود در راهنمای قبلی‌اند؛ اجرای همهٔ تست‌های مرتبطِ تغییر همچنان لازم است. تست پراکسی GPU نیز در `relay/cloudflare/gpu-proxy.test.mjs` نسخه‌بندی شده است.

`phpunit.xml` محیط testing، SQLite درون‌حافظه‌ای، mail/cache/session ساختگی و queue هم‌زمان تعریف می‌کند. `tests/bootstrap.php` در حضور `bootstrap/cache/config.php` متوقف می‌شود. این guard را برندارید؛ checkout پاک بسازید. این تنظیم‌ها به‌تنهایی تضمین نمی‌کنند هیچ تماس خارجی رخ ندهد: مسیرهای provider، پرداخت و پیامک باید fake شوند و اعتبارنامهٔ زنده در محیط نباشد.

عدد تاریخی «۱۲۴۰ تست» معیار فعلی نیست. برای هر اجرا SHA، PHP، اکستنشن‌ها، دستور، نتیجه، failure/skip و زمان ثبت شود. گزارش‌های قبلی به baseline failure اشاره دارند؛ تست اجرا‌نشده یا قرمز را سبز گزارش نکنید.

HTTP 200 برای UI کافی نیست: JavaScript رندرشده، تعامل فرم، سه زبان و نتیجهٔ واقعی را بررسی کنید. تستی که فقط متن کد یا config ساختگیِ خودش را می‌سنجد، اتصال واقعی اجزا را اثبات نمی‌کند.

## ۴. سه زبان و قرارداد رابط

- روت‌های عمومی از closure مشترک سایت برای fa/en/tr ساخته می‌شوند؛ تغییر را در همان مسیر مشترک انجام دهید، نه با سه نسخهٔ مستقل.
- زبان از مسیر URL تعیین می‌شود. لینک‌های سایت در Blade با `lroute()` و config چندزبانه با `lc()`؛ متن رابط با کلیدهای همسان `lang/{fa,en,tr}/ui.php`.
- واحد پول و نمایش را به helper مربوط مانند `site_price()`، `cloud_price()` یا `invoice_money()` بسپارید؛ واحد ذخیره/ورودی هر مسیر را جداگانه مشخص کنید.
- مقدار JS را با serialization امن مانند `@json()` تولید کنید؛ HTML-escape جای serialization جاوااسکریپت نیست.
- دربارهٔ `<?` در Blade/JS، `@context` و `@{{`، CSP، واژه‌شماری فارسی و رزرو فضای هدر، بخش تله‌های CLAUDE را بخوانید. اختلاف `short_open_tag` محلی/سرور در تاریخچه ثبت شده است؛ وضعیت امروز باید سنجیده شود.
- منطقهٔ زمانی کاربر، سرور، برنامه و صورتحساب یکی فرض نشوند. برای هر زمان‌بندی مقدار مؤثر config و زمان UTC ثبت شود.

## ۵. پول و تحویل؛ بدون دوباره‌خرج‌کردن

جریان سنتی ثبت‌شده: سفارش ← فاکتور ← تأیید سروربه‌سرور پرداخت ← `PaymentService::applyPaid` ← صف تحویل ← فرمان زمان‌بندی‌شده. GPU مسیر درخواست ظرفیتِ بدون پرداخت نیز دارد؛ آن را با سرویس پرداخت‌شده یکی نگیرید.

`CloudFraudGuard` و کنترل اعتبار/ظرفیت، قفل‌های وضعیت، شناسهٔ قطعی منبع و ثبت تلاش قبل از تماس provider را حفظ کنید. تایم‌اوت الزاماً به معنی ساخته‌نشدن منبع نیست؛ ابتدا نتیجه را تطبیق دهید. برگشت وجه/اعتبارِ جبرانی باید یکتا و قابل حسابرسی باشد؛ آن را با سیاست برداشت ماندهٔ کیف پول اشتباه نگیرید.

برای منابع ابری، شرط `server_id` را به‌تنهایی نشانهٔ قابل‌تحویل‌بودن نگیرید. خطای ساختاری و نبود ظرفیتِ گذرا یک سیاست ندارند. جواب ناشناخته موفقیت نیست؛ رویداد مهم با ابزار رهگیری موجود ثبت شود، بدون چاپ رازها.

نام واقعی provider و خطای خام آن به خروجی مشتری نرود. `CloudManager` بین `label()` مشتری و `realLabel()` مدیر تفکیک دارد. وجود در `DRIVERS` با فعال‌بودن حساب provider یکسان نیست.

## ۶. اعلان، نقش‌ها و اتوماسیون

کاتالوگ رویداد، رجیستری الگوی پیامک و نگاشت n8n باید سازگار باشند؛ متغیرهای template کامل باشند. متن ایمیل/بله در پنل، جای متن الگوی تأییدشدهٔ اپراتور پیامک نیست. کانال سفیرِ مشتری و رباتِ مدیر را قاطی نکنید.

راهنمای قدیمی `relay/n8n/README.md` هنوز زنجیرهٔ بله را توضیح می‌دهد، درحالی‌که راهنمای فنی جدیدتر مسیر مستقیم HTTPS به n8n را ثبت کرده است. تا تطبیق sender/config و workflow فعال، از سند قدیمی معماری فعال استخراج نکنید. کد workflow باید در Git بازبینی شود؛ انتقال نسخهٔ تأییدشده به محیط n8n انتشار مستقل است.

`admin`، `staff` و API support در `bootstrap/app.php` جدا تعریف شده‌اند. حساب پشتیبانی را با حساب مدیر جایگزین نکنید. استثنای CSRF در endpointهای سروربه‌سرور به معنی عمومی‌بودن نیست؛ قرارداد bearer/HMAC/token و مجوز همان endpoint باید حفظ شود.

هر فرمان پس‌زمینه باید در زمان‌بندی ثبت شود، overlap محدود داشته باشد و **پیشرفت خودش** قابل سنجش باشد. heartbeat سبز اثبات تحویل، صورتحساب یا سلامت تمام صف‌ها نیست. برای بررسی، صف مالی/تحویل را دستی روی تولید اجرا نکنید.

## ۷. پیش از اولین تحویل

[TEAM](../../docs/project/TEAM.md) و [DEPLOYMENT](../../docs/project/DEPLOYMENT.md) را اجرا کنید. دامنهٔ تغییر را کوچک، آزمون‌پذیر و مستقل نگه دارید؛ migration موجود، رابطهٔ مدل و سیاست مالی را جانبی تغییر ندهید. پیش از نوشتن HEAD تازه را بگیرید و کار همکار را حفظ کنید.

هیچ دستور این سند مجوز تغییر تولید نیست. `.env` تولید، دادهٔ زنده، شبکه، cron، خرید/حذف سرویس و ارسال پیام واقعی خارج از شروع محلی هستند. وضعیت پایان کار را دقیق گزارش کنید: ثبت در Git، نصب روی سرور و تأیید تولید سه مرحلهٔ متفاوت‌اند.
